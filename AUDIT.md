# Fast-tier test audit (2026-10-19)

Scope: the hosted fast tier (four server shards, the remaining-checks job,
four Rust nextest partitions, web unit tests and browser smoke) at `38ebfe456`.
Guide: "Testing on the Toilet: Don't Put Logic in Tests". A test states literal
expected values; a loop, a conditional or a computed expectation can repeat the
bug that the test should catch.

Status words used below:

- **Done**: changed in this pull request, with the evidence listed.
- **Proposed**: not changed; the lead decides.

## Evidence sources

- CI runs: the last 400 `CI` workflow runs (2026-10-13 to 2026-10-19), job and step
  durations from the GitHub API.
- Per-test Rust durations: the nextest JUnit reports. CI uploads them only for
  failed or cancelled partitions, so the 102 reports from 2026-10-17 on give the
  times of the passing tests in those partitions. The times are wall times under
  the CI parallel load, so they overstate the time of a test that runs alone.
- Per-suite server durations: the facade `full.log` artifacts (116 logs) and the
  "Ten slowest server suites" lines of green job logs.
- Proven flakes: 11 runs that failed and then passed on a rerun of the same
  commit. Their artifacts are from the failed attempt.
- Local durations: `just test server <suite>` on an 18-core Mac, with a
  temporary `--durations` option on the runner (not committed).

### Provider replay root cause

The nested-delegation fixture fails when a follow-up turn completes before its
`turn/start` reply arrives. A trace of a failed local run shows the order:

1. A child result for the lead is queued; the dispatcher reserves it and sends
   `turn/start`. The event is `dispatching`.
2. The provider reports `turn/completed` for the new turn before the reply.
   The completion handler counts every `dispatching` event except the first
   turn's `:initial` event as input still in flight, so it sets the agent
   `queued`, and it skips the result for the parent.
3. The reply arrives. `start_accepted` marks the event `delivered`, finds the
   turn already completed, and requeues only for `pending` events. The agent
   stays `queued` with no input.
4. The scheduler finds a `queued` agent with no deliverable input and saves it
   `waiting`. Nothing wakes it again.

The lead of the fixture therefore stays `waiting`, and the test reaches its
60 s hang guard. For a worker, the same order loses the result that its parent
waits for. The existing `:initial` exclusion covers only the first turn.

Fix (`codex_runtime.py`, turn completion): the input of the current submitted
start attempt is not counted as in-flight input when that attempt was reserved
while no turn was active (or is bound to the completing turn). A submission
reserved during an active turn can steer that turn and keeps the existing wait
(`test_child_result_waits_for_inflight_input_receipt` still passes).

Regression test: `tests/runtime-contract.py::RuntimeContract::test_follow_up_completed_before_its_start_reply_reports_to_the_parent`.
The fake provider completes the follow-up turn and holds the `turn/start` reply
until the runtime has saved the completion, so the order is fixed. Without the
fix the test fails every time (child `waiting`, one child result); with it the
child is `completed` and the parent has two child results.

The Python notification oracle of the Rust corpora hashes `Runtime.notification`;
its digest is updated with the reason. No corpus case uses a submitted, unbound
attempt reserved while idle, and both notification corpora pass. The Rust
`settle_terminal` path delivers the attempt's own events before it checks for
pending continuation input, so it has no matching change.
