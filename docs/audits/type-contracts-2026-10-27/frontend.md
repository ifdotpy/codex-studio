## What was mechanically scanned versus deeply inspected

The complete candidate corpus has 140 explicit `JSON.parse` calls (110 production, 30 scripts), 440 non-`as const` assertions, 476 non-null assertions, 577 explicit `unknown` keywords, **zero explicit `any` keywords**, 1,563 optional property/parameter signatures, 215 domain-name string signatures and 292 handwritten object/interface declarations. These counts describe syntax, not defects. `JSON.parse`, browser/IDB APIs and library declarations can still introduce inferred any; zero written `any` does not establish soundness. The domain-name scan includes benign scope identifiers, free text and provider-defined efforts; their classification is in the families below. A second AST pass inventories domain-named useState declarations, aliases and string assertions, including inferred/local UI states.

Mechanical pass: every listed source file was token/AST scanned for parser calls, casts/non-null assertions, unknown/any, optional bags, generic result functions, handwritten object types and domain widening; generated references and imports were searched. This is not a semantic whole-program typecheck and cannot prove absence of inferred widening or unsafe external library types.

Deep pass: boundary implementations and their relevant producer/consumer sections were read, including concrete Rust producer paths where a raw frontend payload might have been mistaken for a typed record. **D** in the table means the relevant owner→decode→consumer boundary was traced, not every line of every listed file manually read. **M+D** identifies families with exhaustive mechanical coverage and selected declaration/caller tracing, where deeper behavior remains expressly unresolved. The entire 107k-line handwritten corpus was **not** manually line-read. Families with incomplete provider, persisted-format or lifecycle proof are marked U instead of being silently treated as safe or removable.

R = remove raw Value/unknown/string erasure using its actual owned contract (in TypeScript, generated boundary types; for native commands, typed Rust command decoding plus generated consumers).
O = retain justified opaque/raw boundary.
T = already typed or genuinely local implementation type.
U = unresolved; owner/compatibility/lifecycle proof needed before removal.
Rows with two letters contain explicitly separated subfamilies in the replacement column; they do not assert one blanket disposition for all their files.
P1 = prioritize contract-integrity work; P2 = useful follow-on; P3 = retain/low-priority/local improvement. These are engineering priorities, **not reproduced runtime severity**. Every witness below is proposed only, not run.

All short frontend paths below are relative to `workspaces/client/apps/web/src`, except `scripts/`, which is relative to the web app root. `runtime-*/...` abbreviates `workspaces/runtime/packages/runtime-*/...`; `client-*/...` abbreviates `workspaces/client/packages/client-*/...`. Named OpenAPI schemas belong to `workspaces/runtime/packages/runtime-http/openapi.json`; generated TS lives in `src/generated/api.ts`.

## Enum/literal follow-through and compatibility constraints

- `RequestStatus`, `TaskStatus`, `TransferStatus` runtime values are generated by `workspaces/tooling/apps/repository-checks/generate-api-types.ts:20` from the same named OpenAPI enum schemas. These three are available now; other closed schemas need their own generated values rather than a new handwritten frontend list.
- Replace RequestDto status literals in `questions/questionCardModel.ts:242,262,309`, `agents/WorkerOverview.tsx:39`, `shell/messages/TeamChats.tsx:131,222`, and equivalent request-only branches with `RequestStatus.*`. `sync/entityProjection.ts` already imports this owner.
- `shell/BackgroundTasks.tsx:180,1011,1168,1177` has task branches eligible for TaskStatus values **after** narrowing. `backgroundTaskModel.ts:68` mixes task, monitor and managed-process states (including pending/stopping); the entire set cannot use TaskStatus. `types.ts:156` Agent status is another domain. `TerminalDock.tsx:45` should index TerminalState.
- `CLAUDE_PERMISSION_MODES` already exists in `generated/claudePermissions.ts:2`; `ClaudeSettings.tsx:58` maintains a separate switch of the same values. Use the generated owner for the select/parser while preserving validation of a DOM string. Workspace modes, DeliveryMoment and work-review constants also already have generated owners.
- `Accounts.tsx:493` reads Agent.accountTransfer, whose status is **AccountTransferStatus**, not TransferStatus. Equal current values do not justify sharing the wrong constant. Conversely `ExecutionSettings.tsx:194` TransferResponse uses TransferStatus correctly; its duplicate shape validator is the separate F20 issue.
- `SummaryAccount.status` is string at generated API line 22631; provider models/efforts, plan names, MCP provider status and some agent phases are also upstream-open. Do not claim a frontend-only enum fixes those. Derive the current field, or first close the owner with a compatibility decision.
- Optional fields with distinct missing/null meanings, partial subscription snapshots, stale cache data plus error, UI acquisition stages and journal acknowledged/rejected flags must not be flattened merely to reduce the count. F04/F05/F07/F08/F13/F21/F22/F35 identify where lifecycle proof is still required.

## Limits and implementation order suggested by source evidence

First address existing typed-owner reuse (F15/F17/F18/F19/F20/F23), preserving all operation/identity/freshness checks. Then design the native and renderer command maps at their actual owner (F09-F12/F16). Treat local hydration/journals as a separate migration with explicit legacy and uncertain-outcome witnesses (F02/F05/F07/F08/F22/F24). Provider text/errors/capabilities need upstream compatibility proof before any closed model replaces their raw fallback (F13/F25-F28/F31).

This report does not propose blanket validators on first-party renderer HTTP/SSE, arbitrary unknown variants, provider-hardcoded unions, new state/recovery machinery, or removal of semantic outcome checks. No proposed migration was implemented. No runtime defect is claimed without a future witness. StartWait/serverAccess baseline work remains visible in F41 but does not substitute for the remaining census.
