Neither inventory completeness nor a generated type alone proves fixture correctness. ## Candidate details that matter for verification

1. **Free generic decoding is distinct from valid callback/path generics.** messages/helpers.ts permits `responseJson<T>` and `requestBody<T>` with no relationship to the route. message-receipt-pagination-browser.spec.ts:357 adds `get<T>(path:string)`. In contrast, rust-ui-fixture.ts:291 and workspace/task-review-api.ts:19 accept an actual `Path` and `PostBody<Path>`, returning `PostResult<Path>`; those already preserve the route relationship. `required<T>`, barrier/wait callbacks and `streamTranscriptFixture<T>` preserve the supplied value's type and need no DTO conversion.

2. **Normal fixture builders and intentional malformed fixtures need different treatment.** The broad path overload in accounts/fixture-helpers.ts:119 can claim a generated discriminated union for any string path; servers/browser-fixture.ts:14-39 overlays other union members' fields as optional. Strengthen normal route construction and observations while keeping explicitly named negative-fixture entrypoints. Existing `Partial<Snapshot>`-style service fixtures, missing generation/resourceVersions, old `_syncEntities` and provider-extension records are not evidence of a production protocol bug.

3. **The fixture hook intersection is stronger than its producer.** rust-ui-fixture.ts exports the actual variants but parses into an intersection of notification, create-worker and provider-control data. A create-worker message need not contain provider-control agent/steps. Use the existing local owner to preserve variants, with an explicit adapter for open provider notifications. Do not close arbitrary provider method strings without preserving the test DSL's purpose.
