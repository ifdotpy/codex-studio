# Rust desktop backend and state compatibility

## Scope and evidence

This is a source-only compatibility matrix for the Python runtime at the assigned Rust base. It uses the Python schema owners, [`runtime-state-formats.md`](runtime-state-formats.md), [`runtime-state-schema.json`](../workspaces/runtime/packages/runtime-store/src/runtime-state-schema.json), and Rust store/repository implementations under [`runtime-store`](../workspaces/runtime/packages/runtime-store/src/) plus [`runtime-server`](../workspaces/runtime/apps/runtime-server/src/). No live state directory or live database was opened. Schema fixture names describe source-owned schema, not user data.

Rust store compatibility is repository-scoped. `RuntimeStore::open` validates state structure, checks registered repository table/column/trigger contracts and migration gates, takes `runtime.lock`, prepares sync schema, and recovers checkpoint captures. This does not mean every Python-owned record family is loaded or preserved by a Rust route. Several routes remain refusals on this base; see the cutover inventory. Do not enable the Rust backend for a user state until all required data families and user flows have an accepted compatibility proof.

## Desktop selection and startup

`CODEX_DESKTOP_BACKEND` is owned by [`backend.cjs`](../workspaces/client/apps/desktop/backend.cjs). Missing or `python` selects the existing Python CLI. `rust` selects `studio-runtime-server`; any other value fails startup. `CODEX_RUNTIME_SERVER` may point to an executable for development or tests. Packaged desktop resources contain `bin/studio-runtime-server`.

Both backends receive the canonical `CODEX_AGENTS_STATE_DIR`, loopback port, and desktop process environment; stdout and stderr append to `<state>/canvas.log`. Electron verifies `GET /api/desktop` and requires application `codex-agents`, protocol 1, a lowercase SHA-256 build ID, a live PID, and the exact canonical state directory before reporting readiness. Python's `backend_build` owner hashes every named file in the server source inventory, including each path and file digest (`codex_backend_identity.py:9-22`). For Rust, Electron hashes the selected executable bytes (`backend.cjs:68-90`) and supplies that same ID as `CODEX_BACKEND_BUILD` (`backend.cjs:498`). Before binding its HTTP listener, Rust streams and hashes its own executable once, rejects a valid launcher ID that does not match, and reports the computed executable hash even for direct launches. The desktop identity check requires a newly started Rust backend to report the selected executable hash and accepts the lowercase 64-hex format for either backend (`backend.cjs:282-345`). Rust `RuntimeStore` owns the same `runtime.lock` exclusivity mechanism. Serving opens use `RuntimeStore::open_claiming`, which records the owner marker after the lock and before the first write. Electron writes `<state>/canvas.pid` only after readiness. On exit, Rust removes this file only when it still contains its own PID, while retaining `runtime.lock` until after the check; it never signals a PID read from the file. A start failure is reported with the log path; an uncertain timeout does not trigger a replacement launch.

The selection does not migrate state. Python remains the default until an explicit Rust selection is set. Rust packaging/startup is not a claim that the Rust server implements all Python HTTP behavior.

Rust storage format of 2026-10-20 (volatile agent fields): the agent fields that hot provider notifications change (`events`, `lastEvent`, `activity`, `activeTools`, `tail`, `lastAnswer`, `contextUsage`, `tokensUsed`, `tokenUsageAccounting`) are stored in the Rust-owned table `runtime_agent_volatile`, one row per agent and one column per field holding the field's JSON value, not in `runtime_agents.record`. The owner is [`agent_volatile.rs`](../workspaces/runtime/packages/runtime-store/src/agent_volatile.rs): readers see one merged agent object, writers store the record without these fields only when it changed, and triggers journal a volatile change like an agent record change and delete the row with its agent. A notification that changes only these fields therefore does not rewrite the indexed agent record or wake `runtime_agents` row observers. The first Rust open that creates the table moves the fields of every valid agent record in the same transaction (`migrate_2026_10_20`). A Python runtime or an older Rust build reading such a state sees agents without these fields; the owner marker keeps Python fenced, and rolling back to an older Rust build requires the pre-upgrade backup.

### `analytics.sqlite3` table disposition

The Python fresh-start tables are `analytics_agents`, `analytics_cost_changes_v1`, `analytics_cost_projection_v1`, `analytics_cost_roots_v1`, `analytics_cost_state_v1`, `analytics_history`, `analytics_items`, `analytics_limits`, `analytics_meta`, `analytics_notifications`, `analytics_turns`, `analytics_usage`, and `analytics_usage_roots`. Rust reads the `analytics_meta.fileMigrationV1` gate, maintains the `analytics_limits` lookup index if that table exists, and otherwise leaves the Python analytics data tables untouched. `fileMigrationV1` may be absent or complete; a present non-complete phase is refused. The database has no global schema version; `PRAGMA user_version` is not a rollback fence.

## Rollback procedure and version fence

1. Before the first Rust start, stop writers through the normal coordinated shutdown and make a verified backup of the entire state tree, including both SQLite databases and any SQLite WAL/SHM files, referenced blobs, receipts, supervisor files, and feature sidecars. Record the backup identity and the Python and Rust executable build IDs. Do not make a file-by-file live copy while a backend owns the directory.
2. Start Rust only by explicitly setting `CODEX_DESKTOP_BACKEND=rust`. Keep the Python executable and its known-good launch configuration available. Do not change the canonical state directory or attempt a parallel Python start.
3. To roll back, stop the Rust process and confirm the exclusive `runtime.lock` is released. Preserve the Rust-mutated state tree and the backup as separate recovery points. Do not copy selected tables back over the Rust tree, delete WAL files, reset `user_version`, or replay an operation whose outcome is unknown.
4. The Rust server writes `<state>/rust-state-owner.json` atomically while it holds `runtime.lock` and before its first write to the state ([`state_owner.rs`](../workspaces/runtime/packages/runtime-store/src/state_owner.rs)). Every entry point is fenced the same way: desktop, launchd recovery, systemd or a direct start. The marker contains `runtime=rust`, `formatVersion=1` (the state format this Rust build writes), and the executable SHA-256 build ID. A later Rust build with the same format takes over the marker and records its own build; an unknown runtime, a malformed marker or another format version is refused before any write. Python's `codex_state.state_dir()` checks this marker before Python callers open state and fails closed unless `(formatVersion, backendBuild)` appears in `PYTHON_COMPATIBLE_RUST_STATE_OWNERS`. That allowlist is empty because no cross-runtime write compatibility proof exists. Keep it empty during rollback; restore the complete pre-Rust backup to an isolated recovery copy and validate it there. Never point Python at the Rust-mutated directory without an explicitly proven pair in the allowlist.
5. Do not use `PRAGMA user_version` as the fence: it remains zero and is not monotonic. A compatibility proof must cover the exact Rust build and state format, including every changed row/file, and update Python's named allowlist only after review. Malformed or unknown markers remain blocked. If the desktop cannot write or verify the owner marker, it must not launch Rust.

The marker is a rollback fence, not a state migration. A Rust start that stops before it holds `runtime.lock` made no write and leaves Python able to open the state; once the marker exists, Python stays fenced until the pre-Rust backup is restored.

## HTTP parity notes from rehearsal 2

The deleted-agent monitor-log response is compatible: Python `monitor_log` validates its owner at `codex_workspace.py:2154-2167`, and `checked_actor` raises `ValueError("This agent was deleted")` at `codex_work.py:984-994`; the Python HTTP endpoint is `studio_api/io/router.py:217-249`. Rust returns the same HTTP 400 message, so this response is expected parity rather than a Rust defect.

Rust treats invalid persisted data encountered by the monitor-log route—including a malformed monitor record or unsafe log path—as unavailable: `GET /api/monitor/log` returns HTTP 503 with a generic error body. This keeps malformed persisted state fail-closed without returning the stored object ID or filesystem path. Unexpected route and storage failures still use the normal internal-error response.

Python has no `GET /api/agents` or `GET /api/monitors` list route. Its agent router defines `POST /api/agents` at `studio_api/agents/router.py:177-185` and the separate `GET /api/agents/finder-view` at `324-335`. Agent and monitor lists are supplied through sync entities; no additional Rust list routes are required.
