# Codex harness mechanisms and Studio comparison

- Repository: <https://github.com/openai/codex>
- Pinned commit: `1bf73324cadc72a53ed467edc7d3fd2b145a6166` (2026-09-25)
- Research date: 2026-09-25
- Scope: Rust core (`codex-rs/core`), app-server and its v2 protocol. Studio comparisons cite this checkout. Findings describe source, not live behavior.

## 1. Input while the agent works

Codex Core owns the admission decision. `turn_input::handle` decides to start, steer, reject or defer submitted input, then returns its decision without waiting for model sampling ([turn_input.rs, lines 1-11](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/core/src/session/turn_input.rs#L1-L11)). App-server `turn/steer` requires the caller's expected active turn ID and records that ID against the request ([turn.rs, lines 293-315](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L293-L315), [turn_processor.rs, lines 1027-1074](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/request_processors/turn_processor.rs#L1027-L1074)). Core places steer input in the active turn's pending input queue; the sampling loop watches queue activity and can consume it in that turn ([input_queue.rs, lines 88-135, 220-270](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/core/src/session/input_queue.rs#L88-L135)). Other input modes can start a new turn when idle. Core also defers inputs it cannot safely steer. Parent-to-child messages use a separate inter-agent mailbox and may trigger an automatic turn ([input_queue.rs, lines 138-202](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/core/src/session/input_queue.rs#L138-L202)).

Studio stores queue/steer/after_tool intent. A steer goes to native `turn/steer` with a `turnId` precondition; otherwise queued rows are selected by Studio's dispatcher at turn start ([`codex_runtime.py`, lines 1727-1827, 1837-1937, 2396-2464](../../scripts/codex_runtime.py#L1727)). **Assessment: weaker** for ordinary queue delivery: Studio's default waits for turn end, while Codex can accept steering during a running turn. Studio's explicit modes are useful product policy, but the default can strand urgent input. Proposal: offer native steer as the default for eligible user and agent messages, and retain queue as an explicit mode.

## 2. Turn and session state ownership

Codex Core owns the active turn and its input queue. App-server keeps per-thread state for the client-facing event projection, current/last turn history, pending interrupt receipts, and listener lifecycle ([thread_state.rs, lines 91-115, 197-218](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/thread_state.rs#L91-L115)). Thread history and rollout state are backed by the thread store; a daemon recovery snapshot records root thread IDs and restores them through normal cold resume ([daemon_thread_recovery.rs, lines 1-49](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/daemon_thread_recovery.rs#L1-L49)). The app-server listener orders notifications and requests. It records a terminal turn ID before clearing active history; interrupt replies are matched to that turn's abort event ([thread_state.rs, lines 197-218](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/thread_state.rs#L197-L218), [turn_processor.rs, lines 1608-1640](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/request_processors/turn_processor.rs#L1608-L1640)).

Studio owns durable orchestration rows in SQLite and mirrors native `inFlight` and `turnId` from callbacks. A shared event queue serializes callbacks for one connection; turn state can therefore lag native events ([`codex_runtime.py`, lines 304-315, 574-680, 2956-3048](../../scripts/codex_runtime.py#L304)). **Assessment: weaker** as a second authority. Codex also has a projection, but its Core turn object and app-server listener share the in-process session lifecycle. Proposal: keep SQLite as the durable orchestration source, but make native state authoritative for active-turn status and reconcile by turn ID before every delivery decision.

## 3. Subagents and multi-agent work

Codex `spawn_agent` reserves capacity, creates a child thread (or fork), persists the parent-child edge, then submits the initial input ([spawn.rs, lines 630-769, 806-850](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/core/src/agent/control/spawn.rs#L630-L769)). Agents exchange structured messages through collaboration tools and inter-agent mailbox input. `wait_agent` awaits child status/results up to a requested timeout; it is an explicit model tool, not parent-side polling of a Studio database ([multi_agents_v2/wait.rs, lines 1-110](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/core/src/tools/handlers/multi_agents_v2/wait.rs#L1-L110)). Each child has its own thread and lifecycle notifications. Result arrival follows child completion; mailbox queue ordering is maintained per recipient, not a global order across children ([input_queue.rs, lines 138-202](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/core/src/session/input_queue.rs#L138-L202)).

Studio creates native threads but also coordinates them in its server, SQLite task board and message tables; it wakes the parent with result events. It does not make the parent block while child work runs. **Assessment: broadly equal** on asynchronous work and separate transcripts; Codex is simpler for native thread-to-thread collaboration, Studio is stronger for durable cross-agent task tracking and user inspection. Proposal: avoid duplicating completion/status concepts across task board and event rows; define one durable child-result record and derive UI status from it.

## 4. Long-running commands and background work

Codex's `command/exec` protocol supports process IDs, stdin/stdout streaming, resize and terminate ([command_exec_processor.rs, lines 35-83, 102-170](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/request_processors/command_exec_processor.rs#L35-L83)). Core command tools execute within the active turn and report results to the model. The app-server command API is for client-managed processes; callers receive stream events and can send writes, resize and termination. `wait_agent` provides an event-driven wait for child work, not a periodic status query ([wait.rs, lines 45-110](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/core/src/tools/handlers/multi_agents_v2/wait.rs#L45-L110)).

Studio adds durable command monitor rows, a separate executor, result delivery and monitor-exit recovery. **Assessment: justified** for commands that must outlive a model turn or be managed in Studio's background panel. Codex's process stream is a simpler native building block, but does not alone provide Studio's durable UI and cross-turn ownership. Proposal: keep monitor feature; reuse one command lifecycle and receipt model across Codex and Claude paths.

## 5. Failure handling

Codex has explicit turn interrupt with a turn ID. App-server checks that ID against the active turn, submits Core interrupt, and answers after the matching abort event ([turn_processor.rs, lines 1600-1645](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/request_processors/turn_processor.rs#L1600-L1645)). A daemon restart snapshots root threads and restores through cold resume ([daemon_thread_recovery.rs, lines 10-49](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/daemon_thread_recovery.rs#L10-L49)). App-server also has native turn error categories such as usage limit, rate limit and server overload ([shared.rs, lines 102-132](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server-protocol/src/protocol/v2/shared.rs#L102-L132)). The inspected code does not establish Studio-style durable automatic reissue after a terminal overload or usage-limit turn; do not infer that the entire model transport never retries internally.

Studio marks requests uncertain after lost acknowledgements and avoids replay without a receipt; it additionally has context repair, capacity retry and usage resume flows. **Assessment: stronger** in explicit orchestration-level uncertainty and user-visible retry control, but materially more complex. Proposal: preserve exact request identities and uncertainty; evaluate whether the recovery layers can be composed as one persisted retry/reconcile state machine.

## 6. Concurrency and storage

Codex uses async per-thread mutexes, bounded or unbounded channels for specific ordered flows, a thread store for history and optional durable queued submissions. `thread/queue` exposes add/list/update/delete/reorder against the queue service ([thread_queue_processor.rs, lines 75-180](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/request_processors/thread_queue_processor.rs#L75-L180)). Per-thread listener channels order serialized state changes. Thread state is not guarded by one process-wide lock ([thread_state.rs, lines 316-360](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/thread_state.rs#L316-L360)).

Studio uses SQLite WAL, one Python runtime `RLock`, and a per-connection callback dispatcher. The dispatcher queue has a limit, coalesces text deltas, sheds selected deltas under pressure, and disconnects on saturation rather than silently dropping a request ([`codex_runtime.py`, lines 300-315, 574-598, 620-680, 740-805](../../scripts/codex_runtime.py#L300)). **Assessment: weaker** under many simultaneous agents because unrelated DB and state operations contend on the global lock; per-thread ownership is a better target. Studio's explicit bounded-queue failure behavior is prudent. Proposal: gradually split the global lock by account/agent and keep short transactions for shared indexes.

## 7. Other useful harness differences

Codex's native multi-agent model has parent-child thread identity, collaboration tools, mailbox delivery, wait and interrupt built into Core. Studio's user-facing task board, request receipts, team rooms, cross-provider account selection and durable monitors are separate features, not direct equivalents in the inspected Codex path. Studio is stronger when users need explicit status, audit history and recovery across a backend restart. Codex is simpler when agents only need to delegate and exchange messages.

Codex's API makes active-turn preconditions first-class: `turn/steer` requires `expectedTurnId`; `turn/interrupt` requires `turnId` ([turn.rs, lines 293-335](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L293-L335)). Studio already uses this guard for steer and extends identities with account, thread, epoch and request ID. **Assessment: justified**, with a maintenance cost. Keep the larger identity at durable boundaries; use the native turn ID for live-turn decisions.

## Anomalies in Studio code

These are design questions, not confirmed defects. “Root decision” is an inference unless noted. Proposals are scoped to mechanisms that have no direct counterpart in the inspected Codex path.

1. **Mirrored live-turn state.** [`codex_runtime.py`, lines 1033-1047, 2956-3048](../../scripts/codex_runtime.py#L1033) persists `inFlight`, `turnId` and status from native callbacks. Codex Core owns its active turn; app-server derives a current-turn view from ordered events. **Why does Studio need the mirror?** Inference: SQLite must coordinate work across server restart and provider sessions, but the copy can lag. Root decision: split orchestration state from native session ownership. **Proposal:** keep durable lifecycle state, derive live status from native thread status and reconcile before send/start.

2. **Single callback queue in front of every agent event.** [`codex_runtime.py`, lines 300-315, 574-680](../../scripts/codex_runtime.py#L300) serializes connection callbacks, caps the queue, batches deltas and disconnects when full. Codex routes each thread through its own listener and state lock. **Why does Studio need global per-connection callback serialization?** Inference: Python callback mutation touches shared SQLite/runtime state. Root decision: one dispatcher and global state manager. **Proposal:** dispatch by thread/account to bounded per-thread queues; retain explicit saturation errors.

3. **Queue-notice steer workaround.** [`codex_queue_notice.py`, lines 1-49](../../scripts/codex_queue_notice.py#L1) waits 15 minutes, then steers a warning that pending inputs still cannot reach the agent. Codex has pending steer/mailbox input activity delivered in-turn. **Why tell an agent it cannot receive queued input?** Root decision: default Studio message delivery waits for the next turn. **Proposal:** allow urgent eligible input to steer; keep notice only for explicit queue mode.

4. **Context-repair fork pipeline.** [`codex_context_repair.py`, lines 1-60, 978-1015, 1058-1127](../../scripts/codex_context_repair.py#L1) verifies historical event receipts and repairs a thread by forking, while refusing to repeat an ambiguous fork. The inspected Codex path uses native thread history and input queue; no parallel repair-fork mechanism appeared in the inspected files. **Why can an accepted event need a later history repair?** Inference: Studio's callback lag plus separate event ledger can make native context and Studio acceptance disagree. Root decision: separate persisted event queue and native prompt history. **Proposal:** prevent divergence with native receipt/reconciliation at delivery; retain repair only as a manual, audited migration tool.

5. **Automatic capacity retry scheduler.** [`codex_capacity_retry.py`, lines 1-25, 54-96, 105-195](../../scripts/codex_capacity_retry.py#L1) persists overloaded-turn retry identities, schedules delays, checks current workspace/account/budget, and caps attempts. Codex exposes terminal overload as a native turn failure in the inspected protocol; its internal transport retry policy is outside this evidence. **Why retry a completed failed turn in Studio?** Inference: the UI orchestration layer wants autonomous recovery after native terminal failure. Root decision: Studio owns turn scheduling. **Proposal:** merge overload and usage retries into one policy engine, with provider-specific retry classification.

6. **Separate usage-resume subsystem.** [`codex_usage_resume.py`, lines 1-55, 90-190](../../scripts/codex_usage_resume.py#L1) keeps scheduled resumes, refreshes rate-limit windows and resumes when capacity returns. Codex reports native usage/rate-limit errors; inspected source does not show a Studio-like resume scheduler. **Why poll account windows outside the owning harness?** Inference: Studio wants cross-agent account-level resumption. Root decision: Studio centrally schedules agents and owns account budgets. **Proposal:** share the retry state machine with item 5 and resume only after a confirmed native eligibility update.

7. **Recovery tick chain.** [`codex_runtime.py`, lines 2415-2432](../../scripts/codex_runtime.py#L2415) calls independent context, turn, connection, browser and notice recovery services on dispatcher ticks. Codex uses native cold resume of root threads after daemon restart ([daemon_thread_recovery.rs, lines 31-49](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/daemon_thread_recovery.rs#L31-L49)). **Why can one interrupted turn require several parallel recovery records?** Inference: independent Studio subsystems own partial lifecycle facts. Root decision: recovery is feature-local. **Proposal:** define one recovery coordinator with typed causes and receipts; leave provider-specific remediation as handlers.

8. **Startup mutation of uncertain work.** [`codex_runtime.py`, lines 826-828, 1033-1054](../../scripts/codex_runtime.py#L826) changes reserved/dispatching events to uncertain, clears attempts and marks active turns interrupted after disconnect. Codex resumes persisted thread history through native server recovery. **Why must Studio rewrite active work state before it can reconcile?** Root decision: local DB needs to recover independently of app-server callbacks. **Proposal:** persist immutable attempt records and reconcile them against native thread history before classifying interruption.

9. **Per-agent epochs layered over native turn IDs.** [`codex_runtime.py`, lines 1038-1047, 1791-1797](../../scripts/codex_runtime.py#L1038) binds work to a local epoch, account, thread and turn to reject stale completions. Codex's live turn operations use thread plus expected turn ID, and listener generations fence replaced listeners ([turn.rs, lines 312-335](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L312-L335), [thread_state.rs, lines 126-142](https://github.com/openai/codex/blob/1bf73324cadc72a53ed467edc7d3fd2b145a6166/codex-rs/app-server/src/thread_state.rs#L126-L142)). **Why does Studio need another generation token?** Inference: transfers/deletion can replace native thread identity while delayed callbacks remain. Root decision: Studio supports cross-account transfer and durable tombstones. **Proposal:** retain epoch only for transfer/deletion fencing; document it as identity generation and avoid using it as a second turn state.

10. **Account-level polling and lock layer.** [`codex_runtime.py`, lines 757-766](../../scripts/codex_runtime.py#L757) keeps account rate-limit snapshots and per-account refresh locks alongside the global lock. Codex protocol reports rate-limit errors and notifications; Studio adds account admission across its agent pool. **Why does a per-account native signal require local cached state and locks?** Inference: Studio admits many independent agents against shared account capacity. Root decision: cross-agent concurrency and budget control. **Proposal:** keep one account scheduler, use event-driven limit updates, and isolate its lock from per-agent state.

11. **Provider protocol adapter with a second persistence model.** [`codex_runtime.py`, lines 304-330](../../scripts/codex_runtime.py#L304) chooses either Codex app-server or Claude bridge; [`bridge.mjs`, lines 1-60](../../scripts/claude_bridge/bridge.mjs#L1) maps Claude SDK queries to Studio RPC and stores its own JSON session snapshots. Codex itself uses its native app-server and thread store. **Why must Claude emulate a Codex-shaped bridge and own a separate session store?** Inference: Studio chose one orchestration caller interface across different providers. Root decision: provider-neutral runtime layered over provider-native session stores. **Proposal:** keep a narrow provider interface, but align lifecycle and receipt semantics; do not mirror transcript state beyond what the adapter requires.

12. **Separate global, tool, coordination and recovery pools.** [`codex_runtime.py`, lines 763-766](../../scripts/codex_runtime.py#L763) partitions work across four fixed thread pools. Codex uses Tokio tasks and per-thread channels rather than these fixed Python pools. **Why are concurrency controls split by operation class and fixed worker counts?** Inference: prevent long model/tool requests from starving coordination. Root decision: synchronous Python runtime and shared dispatcher. **Proposal:** measure queue delay per pool, then consolidate pools behind bounded async/task queues or retain only limits that prevent demonstrated starvation.

## Studio decisions to reconsider, ranked by impact

1. **Deliver urgent input during active turns.** Evidence: Codex's pending-input queue supports active-turn steering; Studio queue mode waits for its dispatcher, and emits a notice that input cannot reach the agent. Proposal: make steer available as the normal eligible path; preserve queue for deliberate next-turn sequencing.
2. **Reduce copied active-turn state and global lock scope.** Evidence: Studio stores `inFlight`/`turnId` from a serialized callback queue under one runtime lock; Codex keeps authoritative Core turn state and per-thread listeners. Proposal: treat native state as authoritative for live turns; move Studio mutable orchestration state to per-agent/account transactions.
3. **Unify retries and recovery.** Evidence: distinct context-repair, capacity-retry, usage-resume, connection-recovery and turn-recovery paths. Proposal: one typed, durable recovery state machine with exact native receipts and provider handlers.
4. **Retain the useful Studio-only surface.** Evidence: SQLite task/message history, monitors, cross-provider accounts, and explicit unknown-outcome handling have no direct equivalent in the inspected native multi-agent path. Proposal: preserve these product capabilities while removing duplicated turn lifecycle ownership.
