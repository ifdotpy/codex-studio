## 1. Input while the agent works

OpenCode’s HTTP prompt handler calls `SessionPrompt.prompt`, which saves a user message and then calls the session loop. The loop enters `SessionRunState.ensureRunning`. Its per-session runner returns the active run’s completion promise when it is already running. It does not steer or interrupt that run. After the current model/tool cycle, the loop reloads persisted messages and follows the newest user message. Thus the caller waits for the shared run, and the runner decides whether to start or join work. Sources: [`prompt.ts:1052-1071`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/prompt.ts#L1052-L1071), [`prompt.ts:1081-1096`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/prompt.ts#L1081-L1096), [`prompt.ts:1343-1347`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/prompt.ts#L1343-L1347), [`runner.ts:115-138`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/effect/runner.ts#L115-L138).

Studio stores input in its SQLite event queue and defaults to `queue`. It also offers explicit `steer` and `after_tool` delivery. The dispatcher normally gives queued input to the agent at its next turn start. OpenCode’s persisted session history is a simpler queue for subsequent model steps, but does not expose Studio’s explicit live-steer policy. Studio’s extra delivery choices are justified by its separate-agent messaging and user controls; the mirrored in-flight status makes the boundary harder to coordinate. See [`codex_runtime.py:1727-1840`](../../scripts/codex_runtime.py#L1727) and [`ORCHESTRATION.md`](../../ORCHESTRATION.md).

## 2. Turn and session state ownership

OpenCode stores session, message, and part records in SQLite. Session prompt/run ownership is a per-session `Runner` in `InstanceState`; the runner state and session busy/idle status are in memory. Durable session history is therefore authoritative for conversation content, while the running fiber is authoritative for current execution. The HTTP API reads or streams session records and events. Sources: [`session/sql.ts:22-98`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/core/src/session/sql.ts#L22-L98), [`session.ts:486-499`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/session.ts#L486-L499), [`run-state.ts:35-69`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/run-state.ts#L35-L69).

A second prompt saves its message before entering the runner. `SynchronizedRef.modifyEffect` makes the runner transition atomic, so a caller either starts a runner or waits on the existing one. This avoids a separate “turn ended versus new input” queue race inside that process. OpenCode publishes status and message events, and exposes durable-event sync separately. Sources: [`runner.ts:115-138`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/effect/runner.ts#L115-L138), [`status.ts:26-50`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/status.ts#L26-L50), [`event-v2-bridge.ts:19-60`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/event-v2-bridge.ts#L19-L60).

Studio persists its own `inFlight` and `turnId` alongside queue and team state, then applies native callbacks through a dispatcher. Its copy can lag native state. OpenCode’s smaller in-memory runner has no Studio-style durable turn mirror. Studio needs durable scheduling across many native threads, but should treat native receipts as evidence and keep the mirror minimal. See [`codex_runtime.py:2956-3067`](../../scripts/codex_runtime.py#L2956) and [`codex_runtime.py:3214-3289`](../../scripts/codex_runtime.py#L3214).

## 3. Subagents and multi-agent work

The `task` tool creates a child session with a `parentID`, applies child permissions, and runs the child prompt. In the default mode, the parent’s tool call waits for child output, which then becomes the tool result. Children are separate durable sessions, but parent-child exchange is mediated by the tool rather than a general message bus. Sources: [`task.ts:131-190`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/tool/task.ts#L131-L190), [`task.ts:200-225`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/tool/task.ts#L200-L225), [`prompt.ts:255-330`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/prompt.ts#L255-L330).

An experimental `background=true` option starts an asynchronous task and injects a synthetic result prompt into the parent when the child finishes. A running task can be extended by reusing its task ID. The default parent-blocking path gives a simple ordering guarantee: child completion arrives as the tool result before the parent loop continues. Background results instead become later parent input. Sources: [`task.ts:256-297`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/tool/task.ts#L256-L297), [`task.ts:316-358`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/tool/task.ts#L316-L358).

Studio adds team message rooms, persistent task/result events, hierarchical stop, and scheduling across many native threads. OpenCode’s task tool does less and has no general peer-message facility. Those Studio features serve broader product needs. The main design choice to reconsider is whether every result and message needs to become another queued native turn.

## 4. Long-running commands and background work

OpenCode’s shell tool runs the process inside the tool call. It streams and bounds output, waits for process exit, and returns the output as the tool result. It races exit against the request abort signal and configured timeout, and kills the process on abort or timeout. It does not require a separate command agent or a polling loop. Sources: [`shell.ts:428-445`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/tool/shell.ts#L428-L445), [`shell.ts:481-559`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/tool/shell.ts#L481-L559).

OpenCode background subagents use a background-job service and completion waiters. The parent can wait inside the tool or return immediately in experimental background mode. Sources: [`task.ts:284-318`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/tool/task.ts#L284-L318), [`job.ts:17-35`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/background/job.ts#L17-L35).

Studio has command monitors that run separately from model turns and expose terminal input, resize, cancellation, and output. OpenCode’s inspected shell tool is synchronous and does not provide that monitor interface. Studio’s monitors are justified for user-visible, interactive background commands; reuse the native command lifecycle where its contract fits. See `ORCHESTRATION.md` and [`codex_runtime.py:4480-4508`](../../scripts/codex_runtime.py#L4480).

## 5. Failure handling

OpenCode cancellation interrupts the session runner and cancels associated background jobs. Its request processor retries classified transient provider failures up to five times with exponential backoff, jitter, and provider `Retry-After` headers. Context overflow is excluded from this retry policy. Sources: [`run-state.ts:77-105`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/run-state.ts#L77-L105), [`retry.ts:26-41`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/retry.ts#L26-L41), [`retry.ts:183-207`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/retry.ts#L183-L207), [`processor.ts:660-691`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/processor.ts#L660-L691).

Conversation records persist in SQLite, but runner fibers and background-job registry are in-memory services. The inspected code does not show a durable per-turn execution lease or Studio-like native acknowledgement ledger. A process restart preserves the conversation records; automatic replay of a command or in-flight turn is not established by these sources. OpenCode’s local process boundary also removes Studio’s app-server callback receipt problem. Studio’s conservative unknown-outcome records are justified at that external boundary. See [`database.ts:22-35`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/core/src/database/database.ts#L22-L35), [`run-state.ts:35-49`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/run-state.ts#L35-L49), and [`codex_runtime.py:289-292`](../../scripts/codex_runtime.py#L289).

OpenCode has transient API retry, but the inspected code has no equivalent to Studio’s delayed automatic continuation after account usage windows reset. It reports some plan limits with an actionable link. Studio’s longer resume path addresses a different limit policy, so retain it only where the provider exposes reliable reset data and the user enables continuation. Sources: [`retry.ts:85-155`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/session/retry.ts#L85-L155), [`codex_usage_resume.py:7-25`](../../scripts/codex_usage_resume.py#L7).

## 6. Concurrency, storage, streaming, and backpressure

OpenCode serializes run ownership per session using a synchronized state reference, while sessions run independently. SQLite uses write-ahead logging, `synchronous=NORMAL`, a five-second busy timeout, and foreign keys. Sources: [`runner.ts:47-68`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/effect/runner.ts#L47-L68), [`database.ts:22-35`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/core/src/database/database.ts#L22-L35).

The event endpoint registers its listener before it starts streaming, then places events into an unbounded queue and emits server-sent events. It sends a heartbeat every ten seconds. Eager registration avoids losing events during response startup. The source explicitly chooses an unbounded queue, so a slow client can accumulate memory; no backpressure bound is visible here. Sources: [`handlers/event.ts:25-41`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/server/routes/instance/httpapi/handlers/event.ts#L25-L41), [`handlers/event.ts:63-85`](https://github.com/anomalyco/opencode/blob/adee738d1e4597a2d0d317ca61a1625eff289efa/packages/opencode/src/server/routes/instance/httpapi/handlers/event.ts#L63-L85).

Studio has one runtime `RLock` around shared agent state and uses one ordered dispatcher for each app-server’s callbacks. It bounds those callback queues and sheds only redundant deltas under pressure. Unlike OpenCode’s per-session runner, this creates shared contention, but Studio also needs atomic admission and ordering across managed agents. See [`codex_runtime.py:295-320`](../../scripts/codex_runtime.py#L295), [`codex_runtime.py:574-684`](../../scripts/codex_runtime.py#L574), and [`codex_runtime.py:742-755`](../../scripts/codex_runtime.py#L742).

## 7. Other advantages and limits

OpenCode has one session/message model across providers and tool calls. A user message is a persisted message, a child is a session created by `task`, and a command is a tool result. The source does not show Studio-style mirroring of an external app-server’s entire turn lifecycle. This reduces state translation and makes the common path easier to follow. Studio’s native adapters are required for Codex and Claude integration, but provider lifecycle logic should stay behind a narrow adapter contract.

OpenCode’s parent-blocking subagent default also makes result ordering clear without a separate team scheduler. Its event listener registration avoids the startup gap. Its per-session runner avoids a global lock for independent sessions. These choices are simpler for one harness process. Studio’s managed queues, user-visible worker trees, durable commands, and multi-provider support justify some added machinery; they do not justify duplicate representations where a smaller boundary is possible.

## Anomalies in Studio code

These items identify design pressure for review. They do not prove a defect. “Root decision” is marked **Inference** when it is not explicit in source.

1. **Mirrored native turn state.** [`codex_runtime.py:2956-3067`](../../scripts/codex_runtime.py#L2956) and [`codex_runtime.py:3214-3289`](../../scripts/codex_runtime.py#L3214) update Studio’s persisted `inFlight`, `turnId`, and status from delayed native callbacks. OpenCode owns current execution in one per-session runner and stores conversation state in its session database. **Inference:** Studio mirrors native state to support durable scheduling and UI queries. **Proposal:** derive fields from a small lifecycle reducer keyed by account, thread, and turn; persist only scheduling state Studio cannot ask the native server for.

2. **Callback queue and global state lock.** [`codex_runtime.py:295-320`](../../scripts/codex_runtime.py#L295) and [`codex_runtime.py:574-684`](../../scripts/codex_runtime.py#L574) serialize native callbacks through an ordered dispatcher; [`codex_runtime.py:742-755`](../../scripts/codex_runtime.py#L742) adds a runtime-wide reentrant lock. OpenCode uses a per-session synchronized runner and direct event publication. **Inference:** Studio needs callback order to reconcile durable receipts and shared team state. **Proposal:** keep protocol ordering, but move per-agent writes and locks to per-agent state; keep only admission and cross-agent transactions global.

3. **Three delivery modes.** [`codex_runtime.py:1727-1840`](../../scripts/codex_runtime.py#L1727) stores `queue`, `steer`, and `after_tool`, with extra promotion and fallback cases. OpenCode persists prompts and serializes a session loop; it has no matching delivery mode API. **Inference:** Studio exposes provider controls to make input latency explicit. **Proposal:** define one durable queued-message contract and one explicit interrupt/steer operation; implement `after_tool` only if the native protocol supports that exact boundary.

4. **Queue-notice turns.** [`codex_queue_notice.py:1-53`](../../scripts/codex_queue_notice.py#L1) periodically steers an agent to tell it that input waits for the next turn. OpenCode needs no notice for persisted prompts: its loop reloads history after a model/tool cycle. **Inference:** this repairs the long wait created by Studio’s default next-turn-only delivery. **Proposal:** replace model-generated notices with a UI queue-age signal; add safe turn-boundary injection only if users need immediate delivery.

5. **Context-repair fork workflow.** [`codex_context_repair.py:1-25`](../../scripts/codex_context_repair.py#L1) and [`codex_context_repair.py:69-109`](../../scripts/codex_context_repair.py#L69) track event receipts, wait for settled inputs, and repair context through a native rollout copy. OpenCode saves prompts directly into session history before entering the runner. **Inference:** repair exists because Studio’s orchestration queue and native transcript can diverge. **Proposal:** make successful native message receipt the sole point that marks an input delivered; use repair only for verified legacy divergence, then remove it when old records expire.

6. **Separate capacity retry state machine.** [`codex_capacity_retry.py:9-60`](../../scripts/codex_capacity_retry.py#L9) and [`codex_capacity_retry.py:131-197`](../../scripts/codex_capacity_retry.py#L131) schedule retries with turn IDs, epochs, claims, and restart checks. OpenCode has a smaller request-level transient retry policy with backoff and a five-retry cap. **Inference:** Studio must restart failed native turns after the app-server reports a terminal capacity error. **Proposal:** share error classification, delay, and attempt accounting with the common retry layer; retain durable turn-level continuation only for errors that end a native turn.

7. **Separate usage-resume poller.** [`codex_usage_resume.py:7-20`](../../scripts/codex_usage_resume.py#L7) polls every three minutes when reset time is unknown, then schedules a continuation after limits clear. OpenCode retries transient requests and surfaces plan-limit actions; no matching delayed task continuation appeared in inspected sources. **Inference:** this supports Studio’s account reset and credit behavior. **Proposal:** use native limit-change events and reset timestamps first; keep polling as a bounded fallback with a visible user setting.

8. **Provider-specific Claude protocol bridge.** [`bridge.mjs:400-429`](../../scripts/claude_bridge/bridge.mjs#L400) and [`bridge.mjs:1125-1240`](../../scripts/claude_bridge/bridge.mjs#L1125) synthesize Codex-like turns, queue input, persist pending steers, and implement interrupt acknowledgements around the Claude SDK. OpenCode’s provider abstraction uses the same session runner and message model. **Inference:** Studio chose a shared Codex-shaped UI while preserving native Claude accounts. **Proposal:** specify a provider adapter contract and keep SDK mapping there; move queue, turn ownership, and receipts into one shared lifecycle component.

9. **Standalone command monitor subsystem.** `ORCHESTRATION.md` defines monitors with output, terminal input, resize, cancellation, and timeout; [`codex_runtime.py:4480-4508`](../../scripts/codex_runtime.py#L4480) manages cancellation. OpenCode runs shell as a bounded synchronous tool call and waits for exit. **Inference:** monitors let users and agents run commands independently from a model turn. **Proposal:** keep the capability, but share process identity, output capture, and cancellation code with the native shell/command path.

10. **Usage accounting and token-budget gate.** [`codex_runtime.py:3208-3214`](../../scripts/codex_runtime.py#L3208) captures native usage; [`codex_runtime.py:3291-3295`](../../scripts/codex_runtime.py#L3291) can stop a team at its token budget. OpenCode records session token totals and cost in its session table, but the inspected task and runner code has no comparable team-wide admission budget. **Inference:** the additional state exists for Studio’s parent-tree budgets. **Proposal:** keep tree budgets, but calculate them from one durable usage ledger rather than copied per-turn counters where possible.

11. **Native turn recovery layers.** [`codex_runtime.py:2415-2432`](../../scripts/codex_runtime.py#L2415) runs context, connection, browser, and turn recovery hooks in the dispatch loop. OpenCode’s inspected lifecycle keeps its runner local and exposes persisted session messages; it does not show recovery for Studio’s independent app-server connection, browser runtime, or context-rollout repair states. **Inference:** these branches compensate for long-lived native threads and external callbacks that can fail independently of Studio. **Proposal:** group recovery by boundary (transport, turn, context, browser), give each one a single state owner, and remove branches that only repair another Studio workaround.

## Studio decisions to reconsider

Ranked by likely impact on correctness and maintenance cost:

1. **Reduce mirrored execution state and global serialization.** Evidence: items 1 and 2; OpenCode’s runner gives each session one atomic execution owner. Proposal: introduce a per-agent lifecycle reducer and per-agent writes while keeping cross-agent admission transactional.
2. **Revisit queue-only delivery and its notice/repair chain.** Evidence: items 3 to 5; OpenCode stores input in canonical message history and resumes it in the session loop. Proposal: use one durable queue, expose queue age in the interface, and deliver only at a receipt-confirmed safe boundary.
3. **Unify retries and recovery policy.** Evidence: items 6, 7, and 11; OpenCode centralizes transient request classification and backoff. Proposal: share retry primitives, then keep product-specific durable continuation only where a provider limit ends a turn.
4. **Unify provider lifecycle adapters.** Evidence: item 8; OpenCode uses one session path across providers. Proposal: have provider adapters own native I/O and keep turn state, queue semantics, and result handling shared.
5. **Consolidate command execution paths.** Evidence: item 9; OpenCode’s synchronous tool path covers the common command case. Proposal: share process/output/cancel code, while retaining Studio monitors for interactive work outside a model turn.
6. **Keep team budgets as a Studio feature.** Evidence: item 10. Proposal: simplify their data source, not remove the user-facing limit.

## Limits

- The OpenCode comparison is source-only at the pinned commit; no build or live server was run.
- “No counterpart” means none was found in the cited session, task, retry, shell, storage, and event paths. It does not claim the whole repository lacks related code.
- OpenCode’s in-memory runner and background-job registry mean source inspection does not establish automatic in-flight work recovery after process restart.
