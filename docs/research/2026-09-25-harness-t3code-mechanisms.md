## 1. Input while the agent works

The T3 provider sends native Codex turn/start requests. Codex accepts follow-up turns while a turn runs; the runtime keeps the active turn ID for interrupt even when the start response gives a queued turn ID ([CodexAdapter.ts:2521-2558](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexAdapter.ts#L2521-L2558), [CodexSessionRuntime.ts:2586-2604](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2586-L2604)). The server accepts and persists the request; Codex decides when it runs.

Studio offers queue, steer, and after_tool. Queued messages wait for a later turn. Steer targets the active turn ([codex_runtime.py:1727-1755](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L1727-L1755), [codex_runtime.py:1813-1827](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L1813-L1827)). This gives Studio explicit delivery choices, but queue-only input cannot reach a long-running turn.

**Assessment:** Studio's explicit modes are useful across providers. Queue-only delivery is weaker for a Codex turn that accepts native follow-ups.

## 2. Turn and session state ownership

Codex owns the native thread and turn. T3 keeps a provider session runtime, persists its binding, and projects orchestration events into SQL read models ([CodexSessionRuntime.ts:1299-1323](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1299-L1323), [ProviderSessionDirectory.ts:47-81](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/ProviderSessionDirectory.ts#L47-L81), [ProjectionPipeline.ts:1057-1071](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/orchestration/Layers/ProjectionPipeline.ts#L1057-L1071)). For the end/new-input race, the runtime keeps the current active ID until Codex reports the next active turn. Stop settles pending approval and user-input requests before sending interrupts ([CodexSessionRuntime.ts:2614-2655](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2614-L2655)).

Studio also stores inFlight and turnId, then reconciles callback events and start attempts ([codex_runtime.py:3066-3099](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L3066-L3099)). The Studio copy can lag because callbacks pass through a dispatcher queue.

**Assessment:** T3's provider runtime is closer to the authority. Studio's mirrored live state is weaker when callbacks lag.

## 3. Subagents and multi-agent work

Codex creates child app-server threads through its native collaboration feature. T3 registers children from thread/started and subAgentActivity, tracks their turns, and emits child lifecycle events as task events ([CodexSessionRuntime.ts:941-957](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L941-L957), [CodexSessionRuntime.ts:1628-1675](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1628-L1675), [CodexSessionRuntime.ts:1741-1779](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1741-L1779)). Codex coordinates children and returns results into the parent turn. No server polling appears in this path.

Studio disables native Codex delegation. It creates separate managed agents and owns their assignment queues, messages, and child results. This supports mixed providers and Studio tree controls, but adds a coordination layer.

T3 maps child signals to task events. The parent uses the native collaboration tool for message and result exchange; the server maps lifecycle events instead of polling. It handles child `turn/started` arriving before `subAgentActivity` by tracking foreign live turns ([CodexSessionRuntime.ts:1947-1983](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1947-L1983)). **Assessment:** Studio's separate-agent model is justified for mixed providers and control. Native delegation is simpler for Codex-only work.

## 4. Long commands and background work

Codex runs commands inside the native turn. T3 converts command output deltas into runtime content events and forwards approval requests to the application ([CodexAdapter.ts:1798-1816](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexAdapter.ts#L1798-L1816), [CodexSessionRuntime.ts:2105-2155](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2105-L2155)). Codex waits for the tool result and continues the turn. 

Studio has a separate command monitor service with process, approval, input, output, cancel, persistence, and recovery paths. A monitor can outlive a model turn. This adds a second command lifecycle.

**Assessment:** The monitor is justified for detached work. It adds duplication when a command belongs to the active model turn.

## 5. Failure handling

Codex can report whether a runtime error will retry ([CodexSessionRuntime.ts:2088-2102](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2088-L2102)). T3 persists orchestration receipts by command ID. An exact retry returns the earlier result; the receipt and event commit together ([OrchestrationEngine.ts:144-172](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/orchestration/Layers/OrchestrationEngine.ts#L144-L172), [OrchestrationEngine.ts:273-305](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/orchestration/Layers/OrchestrationEngine.ts#L273-L305)). The examined T3 path does not add Studio-style automatic continuation after overload or usage limits.

Stop settles pending approvals and user input before interrupt. It interrupts live children with bounded waits, then interrupts the parent ([CodexSessionRuntime.ts:2614-2655](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2614-L2655)). Exact command retries use saved receipts to avoid duplicate writes. The inspected T3 path does not add automatic continuation after overload or usage limits. Studio adds durable retries for exact serverOverloaded failures and a separate rate-limit resume state machine ([codex_capacity_retry.py:9-18, 64-96](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_capacity_retry.py#L9-L18), [codex_usage_resume.py:7-15, 88-135](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_usage_resume.py#L7-L15)). Both track identities and outcomes to avoid blind replay.

**Assessment:** Automatic resume is a Studio product feature. Two separate state machines are harder to audit than one policy.

## 6. Concurrency, persistence, streaming, and backpressure

T3 has a command queue and event pub-sub. It writes events and receipts in a SQL transaction. Each Codex session has its own notification queue and refs ([OrchestrationEngine.ts:84-108](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/orchestration/Layers/OrchestrationEngine.ts#L84-L108), [OrchestrationEngine.ts:273-305](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/orchestration/Layers/OrchestrationEngine.ts#L273-L305), [CodexSessionRuntime.ts:1310-1323](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1310-L1323)). These queues are unbounded in the cited paths. T3 also has a separate live-stream budget, so this does not prove that all client streams are unbounded.

Studio uses durable SQLite queues and a global Python runtime lock. Native callbacks enter a bounded queue and one dispatcher; it coalesces some text deltas and rejects a saturated queue as an unknown outcome ([codex_runtime.py:307-317](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L307-L317), [codex_runtime.py:600-681](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L600-L681)). This defines backpressure, with cross-agent contention risk.

**Assessment:** Both designs protect persistent state. Studio states its callback limit explicitly. Its global lock has a wider contention scope.

## 7. Clear advantages and tradeoffs

T3 keeps native Codex semantics for follow-ups, collaboration, shell tools, and thread ownership. Its event log and command receipts protect application writes. This reduces Studio-specific translation and repair code.

Studio supports independent agent trees, mixed providers, explicit queue/steer choices, detached monitors, automatic usage continuation, and restart recovery. These features explain some added code. T3 also has complex handling for native child-event ordering and stop behavior. It is not simpler in every area.

## Anomalies in Studio code

These are design questions, not confirmed defects. Root causes marked “inference” are hypotheses.

1. **Mirrored turn state.** [codex_runtime.py:3066-3099](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L3066-L3099) copies native turn ID and in-flight state into Studio records. T3 also projects state, but its provider runtime owns the active turn ([CodexSessionRuntime.ts:2596-2604](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2596-L2604)). **Root inference:** Studio needs the copy to schedule its own queue and worker logic. **Proposal:** derive live status from provider events; keep the database copy rebuildable.

2. **One callback dispatcher for all agents.** [codex_runtime.py:313-340, 600-681](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L313-L340) serializes callbacks through one bounded queue. T3 has a notification queue per session and a separate orchestration queue ([CodexSessionRuntime.ts:1310-1318](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1310-L1318), [OrchestrationEngine.ts:96-97](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/orchestration/Layers/OrchestrationEngine.ts#L96-L97)). **Root inference:** one lane simplifies shared SQLite mutations. **Proposal:** serialize per session or aggregate, then use short transactions.

3. **Global runtime lock.** [codex_runtime.py:743-760](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L743-L760) guards runtime state across agents. T3 uses per-session refs and transactional event writes ([CodexSessionRuntime.ts:1310-1323](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1310-L1323), [OrchestrationEngine.ts:273-305](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/orchestration/Layers/OrchestrationEngine.ts#L273-L305)). **Root inference:** many agent operations mutate shared in-memory records. **Proposal:** replace broad lock scope with per-agent locks and transactions.

4. **Tool-boundary delivery.** [codex_runtime.py:1813-1827](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L1813-L1827) maps after_tool to steer only when Studio sees an active turn. T3 uses native turn/start follow-ups ([CodexSessionRuntime.ts:2586-2604](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2586-L2604)). **Root inference:** Studio approximates native follow-up semantics. **Proposal:** remove after_tool for Codex or define it as a native queued follow-up.

5. **Notices for unreachable queued input.** [codex_queue_notice.py:1-53](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_queue_notice.py#L1-L53) injects a notice after 15 minutes because queued input cannot reach the active turn. T3 uses native follow-ups, so this notice has no counterpart in that path ([CodexSessionRuntime.ts:2586-2604](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2586-L2604)). **Root inference:** the queue creates a communication gap. **Proposal:** use native follow-ups; keep notices only for work that cannot be injected.

6. **Rollout rewrite and fork for repair.** [codex_context_repair.py:1116-1221](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_context_repair.py#L1116-L1142) verifies history, copies and sanitizes JSONL, checks receipts, then forks a thread. T3 uses native read and rollback; no automatic rollout rewrite appears in this path ([CodexSessionRuntime.ts:1283-1297](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1283-L1297)). **Root inference:** Studio repairs disagreement between accepted inputs and native history. **Proposal:** remove the dual-write cause; retain repair as a guarded migration tool.

7. **Separate command monitor service.** [codex_runtime.py:4102-4193](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L4102-L4193) runs and persists commands outside native turns. T3 consumes native command output and approval events ([CodexAdapter.ts:1798-1816](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexAdapter.ts#L1798-L1816), [CodexSessionRuntime.ts:2105-2155](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2105-L2155)). **Root inference:** Studio needs detached commands to outlive turns. **Proposal:** merge native command lifecycle where possible; keep separate monitors only for detached commands.

8. **Monitor recovery feeds context repair.** [codex_runtime.py:848-887, 1055-1058](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L848-L887) recovers monitor receipts and marks unknown command outcomes. Context repair separately waits for monitors ([codex_context_repair.py:896-918](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_context_repair.py#L896-L918)). T3 keeps native command items with provider history ([CodexAdapter.ts:1798-1816](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexAdapter.ts#L1798-L1816)). **Root inference:** monitors create a second command truth and recovery boundary. **Proposal:** unify command identities, outcomes, and liveness in one ledger.

9. **Separate overload and usage retries.** [codex_capacity_retry.py:9-18, 64-96](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_capacity_retry.py#L9-L18) retries overloads. [codex_usage_resume.py:7-15, 88-135](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_usage_resume.py#L7-L15) polls limits every 180 seconds when no reset time exists. 10. **Browser reconnect and probe workflow.** [codex_browser_recovery.py:77-104, 149-207](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_browser_recovery.py#L77-L104) performs one reconnect attempt, then sends a read-only verification turn. The target has no equivalent Chrome-runtime reconnect state machine in the inspected provider path. **Root inference:** Studio dynamically registers an external Chrome skill and must recover a lost local browser session. **Proposal:** move reconnect and readiness signals into the browser runtime, then retain only a small provider recovery hook.

11. **Claude protocol bridge.** [bridge.mjs:1-15, 1071-1095, 1168-1195](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/claude_bridge/bridge.mjs#L1-L15) maps the Claude Agent SDK to Studio’s Codex-shaped local session protocol. 12. **Studio-managed child agent fleet.** [codex_runtime.py:1727-1755](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L1727-L1755) and [4070-4088](https://github.com/ifdotpy/codex-studio/blob/b595383f9595b9f6b16e35f6e2713a346deb8f5c/scripts/codex_runtime.py#L4070-L4088) persists cross-agent messages and wakes separate agents. T3’s native collaboration tool creates child threads and routes their lifecycle through Codex ([CodexSessionRuntime.ts:941-957](https://github.com/pingdotgg/t3code/blob/d06f0ff1048d42a156824765316c5a2dc54f5bca/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L941-L957)). **Root inference:** Studio needs independent providers, durable assignments, and user control. **Proposal:** keep Studio-managed agents for those cases; offer native delegation for same-provider Codex work to reduce duplicated orchestration.

## Studio decisions to reconsider

1. **Highest: use native Codex follow-ups for queued input.** Evidence: T3 accepts follow-ups during active turns; Studio queues messages until turn end and injects delayed notices. Proposal: route queue-mode input through native turn/start with stable message IDs.
2. **High: make live turn state a projection.** Evidence: Studio mirrors native turn ID and in-flight state, then repairs delayed callback state. Proposal: read provider session state as authoritative; persist only recovery and display data.
3. **High: unify monitors with command lifecycle.** Evidence: standalone monitors require their own receipts and block context repair. Proposal: use native command items when commands belong to a model turn; isolate detached work in one ledger.
4. **High: remove routine context surgery after fixing input accounting.** Evidence: the repair path copies rollout files and forks. Proposal: retain it for explicit recovery or migration.
5. **Medium: reduce shared lock and callback scope.** Evidence: one runtime lock and dispatcher span agents. Proposal: partition by session, keep database transactions short.
6. **Medium: combine retry policy.** Evidence: capacity and usage resume use separate state machines. Proposal: one policy engine with exact errors and receipt-based resumption.
7. **Medium: use native collaboration where provider and account permit it.** Evidence: T3 delegates child lifecycle and results to Codex; Studio always manages its own agent fleet. Proposal: retain managed children for mixed-provider use, use native children for compatible Codex work.
8. **Lower: move browser reconnect ownership closer to the browser runtime.** Evidence: Studio has a one-off reconnect and verification chain. Proposal: let the browser runtime report readiness and reconnect state directly.
