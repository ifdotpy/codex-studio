# Claude Code in Rust: harness mechanism study

- Repository: [ultraworkers/claw-code](https://github.com/ultraworkers/claw-code)
- Source commit: [`08106b0c3771ef5b4a5aa176acccd460e88b7325`](https://github.com/ultraworkers/claw-code/commit/08106b0c3771ef5b4a5aa176acccd460e88b7325)
- Date: 2026-09-25
- Studio source read: `b595383f9595b9f6b16e35f6e2713a346deb8f5c`

## Target choice and limits

I chose Claw Code because its pinned repository contains a substantial Rust workspace with a conversation runtime, tools, subagents, background tasks, session persistence, and usage/retry handling. Its Rust README lists these components and describes session resume and subagent support ([README lines 83-109, 191-219](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/README.md#L83)). The other Rust results I inspected were a tutorial or an experimental harness, not a more complete implementation of the same CLI harness. The pinned source is a CLI harness, not a desktop coordinator. Its REPL waits for each turn to finish before reading another line. Findings below distinguish that scope from Studio's multi-agent server.

Code references use GitHub links pinned to the commit above. Studio references link to the source files inspected at the Studio commit in the header. “Inference” marks conclusions about design causes.

## 1. Input while the agent works

Claw Code's `run_turn` takes one owned input string, appends it to the session, then synchronously runs the model and tool loop ([conversation.rs:325-354](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/conversation.rs#L325)). The CLI calls it after `read_line` returns; it does not read another prompt until the call returns ([main.rs:7066-7109](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/rusty-claude-cli/src/main.rs#L7066)). A Ctrl-C signal aborts supported hooks, but this source does not turn new text into live-turn input ([main.rs:7588-7602](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/rusty-claude-cli/src/main.rs#L7588)). The CLI user chooses when to submit the next turn.

Studio accepts queued input or native steer input. `Runtime.send` checks and records an event, then `steer` submits it against an expected native turn ID; `queue` waits for later dispatch ([codex_runtime.py:1727-1755](../../scripts/codex_runtime.py#L1727), [codex_runtime.py:1915-1957](../../scripts/codex_runtime.py#L1915)). The delivery choice belongs to the sender, within Studio's native support and validation.

**Assessment: justified for Studio's product.** Live steering and messages among independently running workers need a server-side input path that this single-user REPL does not need. Studio's queued default can still leave recipients unreachable for a long turn; see anomaly 5.

## 2. Turn and session state ownership

Claw Code's runtime owns the live `Session` value and mutable conversation loop. The session holds messages, metadata, model and workspace binding ([session.rs:108-133](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/session.rs#L108)). It appends messages to a JSONL file when persistence is configured ([session.rs:628-661](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/session.rs#L628)); the session store resolves and reloads sessions ([session_control.rs:138-168](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/session_control.rs#L138)). There is no separate client copy of an in-progress native turn ID in this architecture. Calls are sequential within a CLI process.

Studio stores conversation state in the native Codex thread and separately mirrors turn IDs, in-flight status, events, items, and receipts in SQLite. Notifications reconcile the mirror; start acknowledgements bind native turn IDs ([codex_runtime.py:2797-2825](../../scripts/codex_runtime.py#L2797), [codex_runtime.py:2956-3018](../../scripts/codex_runtime.py#L2956)). Studio fences asynchronous results with agent epochs, attempt IDs and turn IDs to prevent an old callback changing a newer turn ([ORCHESTRATION.md:293-301](../../ORCHESTRATION.md#L293)).

**Assessment: Studio's extra state is justified by its split authority and restartable server, but weaker in simplicity.** The target's single runtime is the simpler source of live truth. Studio's duplicate is needed for multi-client UI, durable coordination and native app-server integration, but creates reconciliation work.

## 3. Subagents and multi-agent behavior

Claw Code's `Agent` tool creates an agent manifest and task file, then starts a named OS thread ([tools/src/lib.rs:4095-4172](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/tools/src/lib.rs#L4095)). The child builds its own runtime, runs one prompt, and writes a terminal result to its manifest/output artifact ([tools/src/lib.rs:4175-4209](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/tools/src/lib.rs#L4175)). Parent-visible status and output are read with agent/task tools; the task registry is a process-global `OnceLock` around an in-memory `Arc<Mutex<HashMap>>` ([tools/src/lib.rs:63-73](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/tools/src/lib.rs#L63), [task_registry.rs:105-114](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/task_registry.rs#L105)). I found no durable parent-child message queue or automatic insertion of child results into a running parent turn in these paths. The parent chooses when to inspect results.

Studio creates managed children as separate native threads and persists their assignments, message events and parent-child results. A completed child result enters the parent's durable input queue and wakes a later parent turn ([ORCHESTRATION.md:286-291](../../ORCHESTRATION.md#L286), [codex_runtime.py:1111-1140](../../scripts/codex_runtime.py#L1111)). Children can message active peers through explicit tools.

**Assessment: Studio is stronger for managed fleets; Claw Code is simpler for a CLI subagent.** Its background-task registry is not durable across process exit, so it is not a like-for-like fleet control plane.

## 4. Long-running commands and background work

Claw Code runs ordinary Bash commands asynchronously in its Tokio command path and returns captured output when the process ends ([bash.rs:169-190](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/bash.rs#L169)). A `run_in_background` shell command instead spawns a process and returns its process ID without output ([tools/src/lib.rs:6602-6634](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/tools/src/lib.rs#L6602)). Separately, task tools expose status, stop, update and output access for registered background tasks ([tools/src/lib.rs:891-947](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/tools/src/lib.rs#L891)). The model can continue its tool loop and call task output/status tools. The task registry itself is in memory.

Studio offers durable command monitors. The agent gets a watch ID and finishes its turn; process exit becomes a queued event and starts a later turn ([ORCHESTRATION.md:280-283](../../ORCHESTRATION.md#L280), [ORCHESTRATION.md:286-291](../../ORCHESTRATION.md#L286)).

**Assessment: Studio is stronger for commands that outlive the model turn or server connection.** Claw Code has a shorter same-process tool loop for work that the model can query itself.

## 5. Failure handling

Claw Code records conversation messages and turn events in its session. Errors from API streaming or tool execution return from `run_turn`; the CLI reports failure and has a targeted context-window compact-and-retry path ([conversation.rs:354-382](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/conversation.rs#L354), [main.rs:7785-7801](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/rusty-claude-cli/src/main.rs#L7785)). Its API client has configured request timeouts and retryable errors with backoff ([http_client.rs:9-32](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/api/src/http_client.rs#L9), [error.rs:124-151](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/api/src/error.rs#L124)). Ctrl-C is an interrupt path; resuming reloads persisted session history. I found no remote mutation receipt or automatic recovery of an uncertain live turn.

Studio handles requests whose outcome may be unknown after a timeout or disconnect. It persists exact IDs and receipts, marks uncertain delivery, and avoids replay without evidence ([ORCHESTRATION.md:293-330](../../ORCHESTRATION.md#L293)). It also has separate policies for confirmed server-overload retries and usage-window resume ([codex_capacity_retry.py:75-96](../../scripts/codex_capacity_retry.py#L75), [codex_usage_resume.py:210-260](../../scripts/codex_usage_resume.py#L210)).

**Assessment: Studio's uncertainty discipline is justified at the app-server boundary.** Its chains of special recovery paths are harder to audit than Claw Code's ordinary request retry; keep only paths with a demonstrated native failure mode.

## 6. Concurrency, persistence and event delivery

Claw Code serializes a single conversation loop. Subagents and command tasks use threads/processes; shared task data uses a registry mutex. Session messages persist to JSONL. Agent manifests/results use files, while `TaskRegistry` data is in memory. I found no client event stream or explicit backpressure queue for harness events in the inspected CLI paths ([conversation.rs:129-143](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/conversation.rs#L129), [task_registry.rs:105-114](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/task_registry.rs#L105)).

Studio owns a SQLite event and receipt store and serializes runtime mutations under one `RLock`; its app-server transport uses a reader, callback queue and dispatcher thread ([codex_runtime.py:295-340](../../scripts/codex_runtime.py#L295), [codex_runtime.py:600-635](../../scripts/codex_runtime.py#L600), [codex_runtime.py:737-804](../../scripts/codex_runtime.py#L737)). It bounds callback queues and sheds selected redundant deltas when overloaded ([codex_runtime.py:295-317](../../scripts/codex_runtime.py#L295)).

**Assessment: Studio is justified in persisting cross-process coordination.** The global lock and callback backlog policy deserve measurement under large teams; the target has no comparable cross-agent contention surface.

## 7. Other clear differences

Claw Code's core loop is one `run_turn` over one `Session`, with a direct API client and tool executor ([conversation.rs:129-143](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/conversation.rs#L129)). It does not maintain Codex app-server thread IDs, callback subscriptions, durable event receipts, worker epochs, browser recovery, account pools or a Studio UI projection. This makes its core loop smaller and its state easier to reason about.

Studio's mechanisms support visible multi-provider chats, many concurrent workers, remote clients, durable commands, approvals, budgets and recovery. Those are materially different requirements. Claw Code is simpler partly because it lacks those guarantees, and its in-memory task registry means background work state can disappear when its process ends.

## Anomalies in Studio code

This is a bounded hunt across the supplied runtime, recovery, retry, queue-notice and Claude bridge files, not a claim that every Studio subsystem has been audited. Each root cause below is an **inference** from the code shape.

1. **Mirrored turn state.** [codex_runtime.py:2797-2825](../../scripts/codex_runtime.py#L2797) copies native turn ID and running state into SQLite. Claw Code owns one live `Session` and has no second native server state ([conversation.rs:129-143](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/conversation.rs#L129)). **Root (inference):** Studio adds an app-server boundary and UI projection. **Proposal:** keep durable intent and receipts, derive transient turn status from a compact native-state cache; make reconciliation one component.
2. **Global runtime lock.** [codex_runtime.py:743](../../scripts/codex_runtime.py#L743) guards runtime-wide operations. Claw Code limits its mutex to its task registry ([task_registry.rs:105-114](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/task_registry.rs#L105)). **Root (inference):** shared mutable agent records plus SQLite transaction management. **Proposal:** measure lock hold times, then split by agent/account and keep database transactions short.
3. **Callback queue repair chain.** [codex_runtime.py:295-317](../../scripts/codex_runtime.py#L295), [codex_runtime.py:600-635](../../scripts/codex_runtime.py#L600) add a large ordered callback queue, overload shedding and disconnect behavior. Claw Code's synchronous loop consumes its stream in place ([conversation.rs:368-382](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/conversation.rs#L368)). **Root (inference):** multiplexing native protocol reads, callbacks, and database writes. **Proposal:** merge transport receipt ordering and callback dispatch behind one per-connection event log, then delete redundant callback paths when parity is proven.
4. **Separate start-attempt state machine.** [codex_runtime.py:2562-2655](../../scripts/codex_runtime.py#L2562), [codex_runtime.py:2797-2859](../../scripts/codex_runtime.py#L2797) reserve an attempt, prepare it, bind an acknowledgement and handle late results. Claw Code calls `run_turn` directly and returns its result ([main.rs:7751-7783](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/rusty-claude-cli/src/main.rs#L7751)). **Root (inference):** Studio must handle network timeouts while its child process can still start a native turn. **Proposal:** retain the durable attempt ID, but combine start transitions into one lifecycle module and remove duplicate booleans where the attempt already determines state.
5. **Queue notice compensates for queued delivery.** [codex_queue_notice.py:1-6, 16-52](../../scripts/codex_queue_notice.py#L1) tells an agent that queued events cannot reach its running turn, then steers a notice into that same turn. Claw Code waits until its synchronous turn ends before reading next input ([main.rs:7066-7109](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/rusty-claude-cli/src/main.rs#L7066)). **Root (inference):** Studio chose queued cross-agent messages as default, even when a recipient is busy. **Proposal:** expose a clear steer policy for eligible events and keep notices only for events that must queue.
6. **Context repair reconstructs external state.** [codex_context_repair.py:584-683](../../scripts/codex_context_repair.py#L584) queries native thread, queue, turn and item records under deadlines before repairing context. Claw Code resumes its own saved session file ([session.rs:263-277](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/session.rs#L263)). **Root (inference):** Studio's SQLite mirror and native rollout can disagree after missed callbacks. **Proposal:** replace broad repair logic with one versioned reconciliation contract; keep the current fail-closed path until native evidence proves safe repair.
7. **Nested offline-steer exception.** [codex_context_repair.py:69-108](../../scripts/codex_context_repair.py#L69) repairs an earlier rule that marked a definitely-unsent offline steer uncertain. Claw Code has no remote steer delivery. **Root (inference):** a transport error class erased whether bytes were sent. **Proposal:** make transport submission return `not_sent`, `accepted`, or `unknown` at the boundary; remove the later string-matching repair.
8. **Provider-specific Claude protocol bridge.** [bridge.mjs:841-860](../../scripts/claude_bridge/bridge.mjs#L841), [bridge.mjs:1168-1228](../../scripts/claude_bridge/bridge.mjs#L1168) serializes requests, emulates turn IDs and persists steer state around the Claude Agent SDK. Claw Code calls the provider API directly through its runtime client ([conversation.rs:364-382](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/conversation.rs#L364)). **Root (inference):** Studio standardizes different provider lifecycles behind a Codex-shaped transport. **Proposal:** keep provider adapters, but define a shared lifecycle contract and move ordering/receipt rules out of the Claude bridge.
9. **Dedicated capacity-retry scheduler.** [codex_capacity_retry.py:75-96](../../scripts/codex_capacity_retry.py#L75) persists retries only for a confirmed overload failure and exact turn identity. Claw Code uses request-level retry/backoff ([anthropic.rs:414-456](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/api/src/providers/anthropic.rs#L414)). **Root (inference):** app-server reports an accepted turn that later fails, so request retry cannot resume it. **Proposal:** preserve the scoped scheduler, but unify its durable timer and validation with the common retry policy.
10. **Usage-window resume scheduler.** [codex_usage_resume.py:210-260](../../scripts/codex_usage_resume.py#L210) polls current limits, validates parent/child state, then enqueues a continuation. Claw Code reports provider rate-limit errors and retries eligible HTTP requests; I found no automatic subscription-window wake path ([main.rs:640-641](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/rusty-claude-cli/src/main.rs#L640)). **Root (inference):** Studio runs long-lived work against account-level subscription quotas. **Proposal:** merge this with capacity recovery behind one policy engine, retaining distinct provider-specific evidence inputs.
11. **Duplicated mutation receipts and event rows.** [codex_runtime.py:1755-1804, 1897-1951](../../scripts/codex_runtime.py#L1755) keeps event metadata and runtime event rows, then handles rejected versus uncertain delivery. Claw Code appends messages to session JSONL and has no remote orchestration mutation receipt ([session.rs:628-661](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/runtime/src/session.rs#L628)). **Root (inference):** Studio must make tool-driven mutations safe across lost responses and process restarts. **Proposal:** do not remove idempotency; consolidate the split receipt tables behind one append-only operation record.
12. **Extensive recovery paths for unreachable CLI states.** [codex_context_repair.py:112-145](../../scripts/codex_context_repair.py#L112) combines browser, restart and safety recovery state before deciding whether a thread is idle. Claw Code's REPL owns one synchronous runtime and resumes its persisted session, with no parallel browser client ([main.rs:7066-7109](https://github.com/ultraworkers/claw-code/blob/08106b0c3771ef5b4a5aa176acccd460e88b7325/rust/crates/rusty-claude-cli/src/main.rs#L7066)). **Root (inference):** multiple Studio clients and external native processes can mutate or outlive Studio's view. **Proposal:** keep recovery tied to explicit native capabilities, but group provider/browser cases under one recovery interface and remove paths with no current caller.

## Studio decisions to reconsider

1. **Reduce live-state duplication.** Evidence: anomalies 1, 3 and 4. Proposal: one reconciliation owner for transient turn state; keep durable messages, attempts and receipts.
2. **Unify recovery and retry policy.** Evidence: anomalies 6, 7, 9, 10 and 12. Proposal: one typed outcome model and policy interface; retain separate evidence adapters for disconnect, overload, subscription reset and provider-specific state.
3. **Fix queued-message reachability.** Evidence: anomaly 5 and [ORCHESTRATION.md:286-291](../../ORCHESTRATION.md#L286). Proposal: let senders select queue or steer for supported messages, and show queue age without injecting a notice into the running turn.
4. **Measure and reduce global serialization.** Evidence: anomaly 2. Proposal: add lock-wait/hold measurements and shard only after contention appears in production.
5. **Keep idempotency, simplify its storage.** Evidence: anomaly 11. Proposal: use one durable operation record for identity, lifecycle state and final receipt.
