## Root decision analysis

1. **Studio mirrors provider turn state in SQLite.** Confirmed by runtime_agents, runtime_events, turn IDs, epochs, native history reads and recovery receipts. Lost callbacks create a window where the database may say “running” after native completion. Turn recovery and context repair add native probes, identity checks and guarded transitions. The stale-turn and spawn incidents show this is a repeated boundary, not one isolated bug.
2. **Studio holds input between turns.** Confirmed by durable event queues, steer requeue, queue notices, pending delivery, capacity retries and usage resumes. Every queue needs ordering, age, account, epoch and stale-input rules. Queue notices and retry UI are visible symptoms of this choice.
3. **One global runtime lock and callback dispatcher.** The callback queue preserves ordering; callbacks also touch shared runtime state. Incident measurements tie queue delay and lock hold time to admission latency, and overflow has disconnected native sessions. Fragment coalescing and shedding reduce load but do not remove lock coupling. Evidence: 2026-09-07-fieldview-admission-latency.md, 2026-09-07-lumina-callback-overflow.md, and 2026-09-12-server-timeout.md.
4. **SQLite stores many records as JSON.** Confirmed in table definitions. A few hot paths now use expression indexes, decode caches and precomputed projections. This means repair logic repeatedly validates JSON identity and shape at runtime; JSON as a cause is an inference, not proof that it caused a specific incident.
5. **Studio owns orchestration outside native agent orchestration.** Confirmed for task waves, tool requests, radio/shared chat, user work, complaints and monitors. Durable receipts, status reconciliation and branch isolation bridge separate native calls. This makes Studio coordination survive restarts, but duplicates lifecycle logic the provider may also own.
6. **Claude bridge emulates the Codex protocol.** Confirmed by scripts/claude_bridge/ and codex_claude_controls.py; recent commits align and retire bridges by version. The shim compensates for a shared Studio runtime contract, not native protocol parity. Versioned refresh and retirement limit, but do not eliminate, semantic drift.

## Open questions

- What share of the 74 uncertain events can be proven not submitted, recovered from native history, or remains truly unknown? The event table alone does not answer this.
- The browser incident says 15 recoveries, while this database has two browser_recovery events. Are these different event schemas, state directories, or a retention/import boundary?
- Why do runtime_native_notices contain 66 configuration notices but none of the long-queue notices? Are queue notices written only as runtime events, or are all relevant users past retention?
- Are any usage resumes retained elsewhere after completion? The table has zero rows, so live firing frequency is unknown.
- Many tables store one JSON record, while hot event and analytics tables have explicit columns and indexes. Which record fields dominate decode cost and lock time? Existing incident evidence names lock/callback time but does not attribute all delay to JSON decoding.
- Browser recovery explicitly says its original startup failure remains unresolved. Which exact native discovery condition failed before the repair was added?
- Context repair rewrites Codex rollout headers, but skips Claude and waits for a complete saved tail. What provider API contract would make the rewrite unnecessary while preserving token budgets and tool receipts?
- Radio and regular team/shared-chat code both schedule multiple agents. Which states remain unique to radio, and does usage data show active radio rooms?
- Complaint enforcement blocks lead completion in some states. Are open complaints intended to block every lead, or only complaints with an explicit required response?
- Live patches avoid restart risk but add a second source activation path. How many patches applied successfully, and how many process generations still rely on that path? The inspected table is runtime_native_catalog_updates, not a live-patch receipt table, so it cannot answer this.

## Ranked remove or replace candidates

Ranking uses expected reduction in repair code and operational risk. It does not authorize removal. Each change needs a compatibility plan and measurements.

1. **Replace shared runtime lock ownership with per-account state and bounded callback work.** Expected effect: fewer admission stalls, overflow disconnects and account-wide coupling; may remove some queue shedding. Evidence: callback incidents and 2026-09-12-server-timeout.md. Risk: high. Callback order and shared state invariants can break if locks split without ownership boundaries.
2. **Move frequently read identity/status fields from JSON records into schema columns.** Expected effect: less repeated decode/validation under the runtime lock and simpler indexed recovery queries. Evidence: record-heavy schema, decode-cache and projection commits. Risk: high. Requires migrations, dual-write control and compatibility for old state directories.
3. **Replace rollout rewriting with a provider-supported checkpoint/replay or transcript import contract.** Expected effect: remove the 1,142-line context repair path and lower malformed or incomplete recovery risk. Risk: very high. No evidence that Codex or Claude exposes a sufficient common API; keep guarded repair until it does.
4. **Unify mutation receipts around one explicit operation lifecycle.** Expected effect: less duplicated pending/uncertain/late-result logic across tool requests, native actions, monitors, account transfer and worker launch. Risk: medium-high. Existing receipt tables have different owners, native evidence and retention needs; unknown outcomes must not become retry permission.
5. **Use native multi-agent turn scheduling where it matches Studio’s contract.** Expected effect: reduce custom speaker floors, turn queues and branch coordination. Risk: high. Native orchestration does not prove parity for shared chat, Studio tasks, account selection or isolated Git worktrees.
6. **Consolidate retry schedulers around one lifecycle with typed causes.** Expected effect: easier diagnosis across capacity retry, usage resume, queue aging and renderer/backend recovery. Risk: medium. Timers have different authorization: an empty retry turn, a post-limit continuation and a pre-submission message retry are not interchangeable.

The best near-term removals are duplicate status reads and stale compatibility paths where a native read now proves the outcome. The September 22 protocol cleanup records removal of obsolete compatibility paths. Keep receipts and uncertainty guards until native evidence or schema changes replace their contracts.
