# Studio heavy data paths: measured audit

This historical audit records `/api/state` and `scope=state` measurements;
those endpoint and pull scopes were removed in the pull request that completed
the move to sync entities (round 3), `#11`.

Read-only audit of the live Studio at `127.0.0.1:4620`, on 2026-09-28. HTTP requests made by this audit were GETs only. SQLite was opened with `mode=ro`; no backend was started. Measurements are a point-in-time sample under active workload, not a controlled benchmark. HTTP sizes below distinguish decoded JSON from gzip wire bytes. Rates marked “derived” combine a measured response with the current UI timer; actual views and event frequency vary.

## Endpoint inventory and triggers

The GET dispatcher in `scripts/codex_canvas.py:693-898` covers `/api/session`, `/api/sync/identity`, `/api/sync/pull`, `/api/sync/stream`, `/api/state`, `/api/costs`, `/api/session-cost`, `/api/desktop`, terminal listing/output, directories, tool requests, analytics, accounts, projects, questions, workspace, work, queue, changes, plan, transcript page/item/search/stream, search/item, checkpoints, capabilities, panel, profiles, rules, monitor log, file-info/file, limits, task, complaint, agent-chat, models, import, legacy transcript, and messages. Most are on-demand and small; the ranks above cover those with measured volume, repeated timers, unbounded history, or slow reads. POST-only actions (messages, queue updates, terminal input, uploads, etc.) were not invoked.

Browser triggers: chat state on first synchronization and credential refresh every 30 s; one shared sync stream plus 3 s safety timer; transcript page on selection/page navigation, transcript SSE while selected, 2 s managed fallback only until SSE is live; Workspace resources reload every 5 s only while open; message queue polls every 3 s while active; accounts every 30 s while open; limits every 60 s while visible and on focus/visibility; costs every 5 s while refreshing, then 60 s; usage view and analytics are user-selected. `/api/changes` was sampled directly but its current UI trigger is tied to Workspace revision reload. These source timers provide per-view rates; browser devtools request logs were not read, so actual simultaneous tabs and retries are unknown.

Mobile uses the same `/api/sync/identity`, `/api/session`, `/api/sync/pull`, `/api/sync/stream` family. Transcript projections are scope-specific; measured pull for one scope was 461 KB decoded / 115 KB gzip. `web/src/sync/client.ts` limits background history concurrency to two and closes sync stream when hidden/offline. `/api/sync/pull?scope=messages` and `scope=work` returned 400 without the valid scope identifier; those were not retried. This is a probe limitation, not evidence that the browser makes invalid calls.

## Server-side decode/serialization and limits

`Handler.send` in `scripts/codex_canvas.py` serializes the full Python object with `json.dumps(...).encode()` on every response; gzip is level 3 for JSON above 1 KiB. This creates at least one full-size encoded buffer per request and a second compressed buffer when gzip wins. The measured 27.2 MB state pull therefore transiently allocates roughly that uncompressed body plus a 7.3 MB compressed body, excluding object/decode copies. Snapshot code at `scripts/codex_runtime.py:5340-5420` reads agent/runtime records and builds presentation state; full snapshot additionally includes work data. The client then parses JSON into objects/RxDB documents. Streaming transcript history rebuilds ordered item maps and JSON-serializes SSE frames; repeated full accumulated answer text is the main per-delta amplification.

The database grew in the sample and `runtime_items`/`analytics_items` preserve large history. Existing same-day storage report `docs/verification/2026-09-28-sync-write-volume.md` contains the prior table/dbstat sizes and measured WAL write amplification; this audit did not repeat a long dbstat scan. The current 36.2 GB main file and row counts confirm database growth remains substantial. Analytics GET timing indicates heavy read work; query-specific CPU/scan counts are not exposed in the HTTP response.

## Per-turn and cost interpretation

For a single cold client, full state projection is **27.2 MB JSON / 7.29 MB compressed** before transcript scopes. For each open Workspace minute, add about **5.97 MB JSON / 1.99 MB compressed** at the measured 5-second timer. A conversation history pull adds about **461 KB / 115 KB compressed** when that scope is first loaded or invalidated; further volume depends on message deltas. An orchestration tool call adds a result payload in the sampled several-KB range, with tails above 50 KB; each call's output is one model-context input. Baseline static instructions and shared guidance are about **27.5 KB / ~6.9k rough tokens** per new thread; later turn caching/rebilling differs by provider, and exact token counts were not available. These components must not be summed as if every view or cache miss happens each minute.

## Transcript delta fixture (2026-09-28)

Isolated byte-count fixture; no live database, backend, or installed application was used. Counts are UTF-8 response/SSE payload bytes, excluding HTTP headers, TCP framing, and gzip. The fixture emits a 40,000-byte answer in 54 updates at 0.75-second intervals (40.5 seconds). Before-change frames carry the full accumulated text and order each time; after-change frames carry one initial replacement followed by appended text, with order only in the initial frame.

| Case                                               |                      Before |                               After |           Reduction |
| -------------------------------------------------- | --------------------------: | ----------------------------------: | ------------------: |
| 40 KB streamed answer, 54 SSE updates              |                 1,104,986 B |                            44,137 B | 1,060,849 B (96.0%) |
| Five pulls; 400 items, one item grows on each pull | 2,313,020 B (462,604 B × 5) | 468,676 B (462,604 B + 1,518 B × 4) | 1,844,344 B (79.7%) |

The pull fixture uses 400 JSON items with approximately 1.1 KB of text each. The first pull is the full projection; the next four send one changed item with its item revision and cursor. A lagging cursor that spans several item revisions receives a sparse delta; a cursor older than the retained tombstone floor receives a full replacement. The pull counts include the serialized JSON response envelope. The SSE counts include the `data:` frame envelope. These are repeatable synthetic fixtures, not a live traffic sample.

The same 40 KB answer fixture updated the transcript 54 times in 40.5 seconds. `sync_entities` WAL growth was **444,992 B** in that interval, or **659,247 B/min** normalized to the current 0.75-second flush cadence. The fixture used 4 KiB SQLite pages and disabled WAL auto-checkpointing. Transcript entity rows held only item/order/metadata hashes and revisions; payloads were NULL. WAL growth is a table-fixture measurement, not a device-write estimate.
