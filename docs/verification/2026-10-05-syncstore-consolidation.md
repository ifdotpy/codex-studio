# SyncStore consolidation audit

This historical comparison includes the old `state:chat` contract; the
`/api/state` endpoint and legacy pull scopes were removed in the pull request
that completed the move to sync entities (round 3), `#11`.

The production implementation is [`scripts/codex_sync.py`](../../scripts/codex_sync.py),
loaded by [`scripts/studio_api/context.py`](../../scripts/studio_api/context.py).
The duplicate `scripts/sync/sync_store.py` was removed (304 lines). Its former
line references below are from base revision `ca123f652de64c84129a04d9b39874e3499cef92`.
Production was 654 lines before this cleanup and was not changed.

## Finding

One production edge was reproduced and left unchanged per scope: if a fresh
store calls `push_drafts` before any pull/generation initializes its lazy
version schema, and `runtime_agents` exists, the writer transaction calls
`_ensure_versions` and receives `sqlite3.OperationalError: database is locked`
while that method opens a second connection to create revision tables. RxDB's
normal replication performs an initial draft pull before its push handler, so
the component test follows that path. The HTTP POST itself does not enforce the
precondition. A direct first POST after identity lookup can therefore fail;
an initial sync pull currently works around it. The behavior is preserved by
`test_fresh_store_first_draft_push_reproduces_lazy_schema_lock`, marked
`unittest.expectedFailure`: it asserts the expected successful first write and
records the database-lock failure without changing production semantics.

## Benchmark evidence

The previous benchmark was a scoped-trigger prototype benchmark, not a recorded
production result. The repository's prior sync docs described expected scoped
invalidation counts but contained no saved run numbers, so there is no numeric
baseline to compare. The replacement benchmark measures production's broad
`data_version` behavior; its numbers are not comparable to the prototype.
The replacement's isolated 300-iteration run on this host reported state-pull
latency p50/p95/p99 of **4.200/4.773/5.196 ms** for analytics churn and
**10.687/13.244/14.871 ms** for UI writes. It emitted **0** state documents
for analytics-only writes and **300** for UI writes, rebuilt the state snapshot
**601** times, and serialized **900,015,192** payload bytes for UI writes.
These production measurements are adjacent to the absent prototype baseline,
but are not comparable to scoped-trigger performance claims.
