# Sync write volume and database reclaim

Measured on 2026-09-28 against `canvas.sqlite3` through SQLite `mode=ro` only. The isolated WAL fixture is `python3 -B tests/sync-write-volume.py`. Its rates are for 60 operations in one minute, with 4 KiB pages and auto-checkpoint disabled. The fixture measures WAL file growth, not total device writes. All live file sizes and table counts below came from read-only queries; this change did not modify the live database.

## Live size and growth

The database had 4 KiB pages, about 35.7 GB in the main file, `auto_vacuum=NONE`, and only 105–233 free pages across observations. `dbstat` reported these allocated bytes: `sync_documents` 337 MB (335 MB payload; 662 derived rows and 70 drafts), `analytics_items` 8.00 GB (3.82 million rows), `analytics_history` 1.80 MB (934 rows), `analytics_usage` 3.27 GB (799,294 rows), `runtime_items` 4.28 GB (628,700 rows), FTS content 6.40 GB, and FTS index data 1.86 GB. Indexes and other tables use the remaining space.

In the preceding 24 h, `analytics_items` had 265,580 records, `analytics_usage` 68,255, and `runtime_items` 51,997. If these rates and the current allocated bytes per row persist, they imply about 0.56, 0.28, and 0.35 GB/day respectively, plus about 0.68 GB/day of FTS content and index for new runtime items: roughly 1.9 GB/day across these tables before other indexes and tables. Historical imports can make this day unrepresentative. `analytics_history` mostly replaces rows; `sync_documents` has one row per scope or draft. The compact version table is one small row per derived scope. No analytics, usage, FTS, agent, event, task, receipt, or chat retention is applied. Their future net growth remains unbounded under the owner's data preservation decision.

The FTS content is also the full transcript body when `runtime_items.record` contains only a truncated excerpt. Deleting it would lose chat text. `analytics_items` supplies detailed analytics and reasoning-history views; it remains intact. Session and account costs use `analytics_usage` or native rollout data and are unaffected by the sync change.

## Controlled reclaim plan — not executed

The safely removable data is the old derived `sync_documents` payloads, about 335 MB of current content (about 337 MB of table pages). Draft rows remain. The current 35.7 GB file cannot be reduced to a small fraction without discarding information the owner elected to keep. A one-time deletion alone merely puts pages on SQLite's freelist; `auto_vacuum=NONE` prevents incremental vacuum from shrinking the file. Changing `auto_vacuum` would itself require a full `VACUUM`.

At a maintenance window with all agents and monitors idle, stop the sole backend normally and keep the same state directory. Back up the database and WAL. With one offline SQLite writer, checkpoint the WAL, then in one transaction backfill `sync_versions` for every derived `sync_documents` row not already represented: use its current `seq`, `deleted` flag and SHA-256 of its exact UTF-8 payload. Keep existing newer version rows. Verify every derived scope has a version row, then delete only rows whose `scope != 'drafts'` and commit. This preserves checkpoints even for scopes that have not been pulled since rollout. Check the workspace identity and draft counts.

Run `VACUUM INTO` a new file outside the occupied database name while the backend remains stopped. Allow at least the current database size plus WAL and backup space. Run `PRAGMA integrity_check` and compare protected table counts on the new file. Retain the original as rollback material, atomically swap the checked file into the original `canvas.sqlite3` path, ensure stale WAL/SHM files from the old database are absent, then start the single backend and verify sync identity, draft pull, state pull, and a transcript pull. Do not run `VACUUM`, `VACUUM INTO`, deletion, or a swap against the live database.

## Live patch inventory

Production functions changed or added: `SyncStore.__init__`, `SyncStore.__del__` (new cleanup), `SyncStore.generation`, `SyncStore._ensure_versions` (new), `SyncStore.pull`, `SyncStore.push_drafts`; `AnalyticsHistoryMixin.analytics_history_step`, `AnalyticsHistoryMixin._analytics_history_save`, and `AnalyticsHistoryMixin._analytics_history_record` (new). `write_generation`, `Runtime.dispatch_all`, and `AnalyticsMixin.analytics_agent` have comment-only edits. The HTTP `make_server` closure, handler, and web client have no source changes. A live patch must attach the two new `SyncStore` methods and the new analytics-history method to existing class objects before swapping the existing method code; the live `sync_store` and HTTP handler already held by `make_server` are retained.

New production module-level names are the `hashlib` and `sqlite3` imports in `codex_sync.py`; `re` is removed. New lazy instance fields are `_version_lock`, `_version_reader`, and `_versions_ready`; old `SyncStore` instances acquire them on first use. The new SQLite table is `sync_versions(seq, scope, hash, deleted, updated)`. No constructor rerun, backend restart, or web protocol change is required by the source design. Any live publication still needs its own validated patch and verification against the running backend; none was applied here.

Test changes are the module-level sync assertions in `tests/sync-contract.py`, the new `ImportTests.test_idle_checkpoint_does_not_rewrite` method, and the new fixture functions in `tests/sync-write-volume.py`: `measure`, `legacy`, `version`, `history`, `items`, `runtime`, `agent`, `search`, `growing_item`, `growing_search`, `trigger`, and `schema`.
