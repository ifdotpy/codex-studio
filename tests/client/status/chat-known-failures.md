# Chat browser known failures

- `files/upload-recovery-browser.spec.mjs` — product defect, reproducible cross-tab lost update. Two same-origin tabs concurrently add different attachments. The original `origin/main` assertion with only the now-required API schema header passed 1/3 and lost `tab-a` in 2/3 runs. The reviewer supported the localStorage-staleness hypothesis below and found no better cause. The revised, unskipped 20-pair same-tick loop reproduced at least one lost update in all 5 consecutive runs; each failure came from the final lost-update assertion, with both writes returning true and a surviving value missing one or more pair IDs (for example, run 1 lost pair 13 and retained through `tab-b-13`). The normal sequential-convergence test remains active; the paired `test.fail` test checks only the concurrent lost-update invariant and will become an unexpected pass when the `localDraft` owner fixes it. Product path: `web/src/sync/localDraft.ts:27-35` opens a readwrite IndexedDB transaction, reads localStorage in its get-success callback, and writes the updated value in that callback; `web/src/components/useAttachmentDrafts.ts:24-30` refreshes in-memory scopes on storage events and `:41-51` supplies the functional updater. Hypothesis: IndexedDB serializes transactions but localStorage may remain stale in another renderer process until its storage event arrives, so a transaction can read an old process-local value. A fix direction is to store the draft value in the same IndexedDB object store as the lock, or re-read after a storage event. The assertion was introduced/migrated by `a149dede` in `origin/main`; the original assertion has the same failure and this is not only a fast-browser-tests rewrite. Workaround: avoid simultaneous attachment edits in multiple tabs until fixed.
