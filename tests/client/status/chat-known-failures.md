# Chat browser known failures

- `composer/composer-stability-ui.spec.mjs` — class 3, same product defect family as fbt-shell's 320px composer/header overflow. At 390px, the send control is 5px outside the composer card (`#composer` x=14,width=362,right=376; `#send` x=337.015625,width=44,right=381). Product code: `web/src/components/chat-controls.css:48-57` keeps `.composer-submit-actions` at `flex:none`; mobile wrapping is in `web/src/components/appearance.css:601-609`. The same non-shrinking row is 408px at 320px and scrolls `#root` by 113px; related symptoms are the 320px composer at x=-99 and header toggle at x=-107. Exact origin/main not checked. Suggested fix: allow the submit-actions row to shrink or wrap within the composer at narrow widths while preserving accessible control sizes.
- `files/upload-recovery-browser.spec.mjs` — product defect, nondeterministic cross-tab lost update. Two same-origin tabs start from the same attachment map and concurrently add `tab-a` and `tab-b`; the original `origin/main` spec with only the now-required API schema header added passed 1/3 and lost `tab-a` in 2/3 runs. In failures both tabs' hook state and `localStorage` contained `tab-b` only. Sequential writes pass and remain active; the concurrent check is a separate `test.fixme` to avoid a flaky expected failure. The quota injector uses `codex-studio-uploads` and is restored before these writes; the deletion interruption injector is also restored synchronously before this section. Product path: `web/src/sync/localDraft.ts:27-35` opens a readwrite IndexedDB transaction, reads localStorage in its get-success callback, and writes the updated value in that callback; `web/src/components/useAttachmentDrafts.ts:24-30` refreshes in-memory scopes on storage events and `:41-51` supplies the functional updater. Hypothesis, untested: the value is in localStorage while IndexedDB is only the cross-tab lock; transactions serialize, but localStorage may remain stale in another renderer process until its storage event arrives, so tab B can read its old process-local value inside the correctly serialized transaction. A deterministic fix direction would store the draft value in the same IndexedDB object store as the lock, or re-read after a storage event. The assertion was introduced/migrated by `a149dede` in `origin/main`, and the original check has the same failure; this is not a fast-browser-tests-only rewrite. Workaround: avoid simultaneous attachment edits in multiple tabs until fixed.
