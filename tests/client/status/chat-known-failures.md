# Chat browser known failures

- `models/model-command-ui.spec.mjs` — intermittent composer-context Main agent settings close behavior. Marker-free repeat-ten runs with a validated precondition (visible dialog showing chat A's model before the switch) produced 1 pass / 9 failures solo and 1 pass / 9 failures under eight busy loops. Each failure kept the dialog visible beyond the 2s hidden wait; the pass necessarily hid it after chat B was selected, so it was not a missed-open precondition. Use unconditional `test.fixme(true, reason)` immediately before the hidden assertion and keep its body. When it stays open, it rebinds to B's `gpt-6-astra/medium`; selecting `gpt-5.6-luna` writes B's id and leaves A unchanged. `f4f176f1` lifts `opened` above the agent/role-keyed child but does not state the intended close behavior. A separate Chat settings control is keyed by agent id and closes correctly. The earlier load-only timeout was a locator bug: global `.last()` selected the composer control behind the open Chat settings modal, whose overlay intercepted the click; scope that control to the Chat settings dialog.
- `models/model-command-ui.spec.mjs` — deterministic Escape focus loss after the Main settings picker rebinds. The picker was opened by typing `/model` in `#message` (active before open); clicking chat B while it remained open rebinds the picker, and after Escape the focused repeat-three run failed 3/3. Focus was on `BODY` immediately before Escape and on the `Release lead` sidebar button afterward, not `#message`/`#send`. A keyboard user can close the picker but loses focus to the chat selector. Pin the unchanged focus assertion with unconditional `test.fail(true, reason)` immediately before it. `f4f176f1` moved `opened` into the outer wrapper while the scoped picker child is keyed by agent/account/role, so the chat switch remounts the open subtree.

- `files/upload-recovery-browser.spec.mjs` — product defect, reproducible cross-tab lost update. Two same-origin tabs concurrently add different attachments. The original `origin/main` assertion with only the now-required API schema header passed 1/3 and lost `tab-a` in 2/3 runs. The reviewer supported the localStorage-staleness hypothesis below and found no better cause. The revised, unskipped 20-pair same-tick loop reproduced at least one lost update in all 5 consecutive runs; each failure came from the final lost-update assertion, with both writes returning true and a surviving value missing one or more pair IDs (for example, run 1 lost pair 13 and retained through `tab-b-13`). The normal sequential-convergence test remains active; the paired `test.fail` test checks only the concurrent lost-update invariant and will become an unexpected pass when the `localDraft` owner fixes it. Product path: `web/src/sync/localDraft.ts:27-35` opens a readwrite IndexedDB transaction, reads localStorage in its get-success callback, and writes the updated value in that callback; `web/src/components/useAttachmentDrafts.ts:24-30` refreshes in-memory scopes on storage events and `:41-51` supplies the functional updater. Hypothesis: IndexedDB serializes transactions but localStorage may remain stale in another renderer process until its storage event arrives, so a transaction can read an old process-local value. A fix direction is to store the draft value in the same IndexedDB object store as the lock, or re-read after a storage event. The assertion was introduced/migrated by `a149dede` in `origin/main`; the original assertion has the same failure and this is not only a fast-browser-tests rewrite. Workaround: avoid simultaneous attachment edits in multiple tabs until fixed.
