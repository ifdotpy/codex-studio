# Known product failures

- `tests/native-retained-executable-contract.py::OperatorCloseContract.test_verified_operator_close_allows_a_new_launch_signature`: open a supervised fake AppServer, close its handle through the operator CLI, then open a replacement `ProcessProxy` with a different executable signature while the old proxy's ACK is gated. A test wrapper gates the replacement proxy's first `next_event`; the fake fixture supplies its known initialize receipt so AppServer setup and a `model/list` submission complete before the old proxy's real ACK commits. Releasing the replacement reader then surfaces `Supervisor next failed: Supervisor replay cursor is stale or ahead of the journal`; `ProcessProxy.next_event` (`scripts/codex_process_supervisor.py:1183`) polls with its local read cursor, while `ProcessProxy.ack` (`scripts/codex_process_supervisor.py:1265`) advances only `cursor`; effect: an operator close followed by a new executable launch on the same handle cannot attach; suggested fix: recover/rebase a stale local read cursor from the acknowledged journal cursor before polling; owner: product, not fixed here. Under 16 Python CPU busy loops, an instrumented 50-iteration probe recorded no ACK stall; one pre-ordering-fix iteration unexpectedly passed. The first loaded full-suite run separately timed out waiting for fixture ACK completion after 90 seconds without an internal trace, so that wait's cause remains unidentified. A later loaded full run exposed a fixture race where the replacement reader could set the transport error before AppServer sent initialize; the first-read gate fixed this, and the marked target then reached its specific expected failure in 50/50 loaded repetitions. Do not infer product ACK latency from the untraced timeout; retain 90 seconds as a hang bound until its cause is identified.
