# `studio-runtime-http`

## Change Contract

- **Responsibility:** own the committed OpenAPI authority, generated Rust DTOs,
  schema identity, Axum router and HTTP boundary compatibility rules.
- **Public interface:** `router`, `HttpState`, `api_schema_hash`, and
  `operations`.
- **Forbidden dependencies:** Python runtime modules, SQLite, provider SDKs,
  and the runtime-server application.
- **Invariants:** schema bytes stay canonicalizer-v3 stable; documented but
  unimplemented operations return the common 501 error; synchronous domain
  interfaces remain outside the async edge.
- **Configuration owner:** `studio-runtime-server` supplies listener identity,
  process token, workspace identity, and local diagnostics to `HttpState`.
- **Focused check:** `cargo nextest run -p studio-runtime-http`.

`openapi.json` is the full, human-readable API authority and outlives the Python
application. It is emitted with sorted keys and two-space indentation by the
Python exporter's deterministic JSON writer; Oxfmt intentionally does not own
this file. Run `pnpm run api:generate` to refresh this document, TypeScript
types/hash, and compile the build-generated Rust DTOs. `pnpm run api:check`
checks model/document drift, byte-for-byte TypeScript output drift, and Rust
DTO generation. TypeScript types are rendered from the full document so the
generated client retains its titles and descriptions.

The server removes only OpenAPI documentation metadata, sorts the documented
schema unions and map keys explicitly, then hashes compact JSON with SHA-256.
This is the Rust implementation of Python's canonicalizer-v3 rules, so editing
prose does not change the API hash.

The `workspace_keeps_serde_json_maps_sorted` test in `studio-runtime-http`
checks the normal workspace feature graph and rejects
`serde_json/arbitrary_precision` and `serde_json/preserve_order`.
`arbitrary_precision` changes number values into serde_json's private wrapper
object; `preserve_order` changes `serde_json::Map` from sorted to insertion
order. Canonical output in several crates relies on sorted keys; code that
needs insertion order must parse ordered pairs locally.

Query parameters follow the root `x-query-parameter-contract` in
[`openapi.json`](openapi.json): undeclared names and repeated scalar values are
rejected with a 400 error and query location. Integer query values use ASCII
decimal digits only; number values use JSON number syntax;
boolean values are exactly `true` or `false`. OpenAPI cannot express the global
unknown-name rule, so validators must apply this extension to every operation.

The `/api/workspace/tasks` `cursor` and `before` query parameters are currently
documented as strings because they carry JSON-encoded cursor objects. Their
decoded shapes follow Python's `TaskFeedCursor` and `TaskFeedBeforeCursor`
models in `studio_api/work/models.py`; keep the Rust decoder aligned until the
OpenAPI document can describe and validate these encoded cursor shapes.
JSON Schema considers an integral
decimal such as `1.0` an integer, while Python's strict request models reject
that JSON body representation; current JavaScript clients serialize integral
numbers without a fractional part.

Rust DTOs are generated by `openapi-to-rust` 0.22.0 in `build.rs`, into Cargo's
`OUT_DIR`, and included from there. The generated files and an extra generator
binary are not checked in. The exact generator version is a build dependency
and is pinned by `Cargo.lock`. `jsonschema` is a runtime dependency for
validating requests against the committed OpenAPI schemas. The build-only
generator is a separate dependency graph.

## Route-group pattern

Each route group lives in its own `src/routes/<group>.rs` module. A handler
accepts `State<HttpState>`, `ApiJson<T>`, `ApiJsonOptional<T>`, `ApiHeaders`, or
`QueryParams` and returns `Json<T>` or `Result<Json<T>, ApiError>`. The boundary
validates each registered request before invoking a handler, and the extractors
read the resulting `ValidatedRequest`; a raw body handler therefore runs only
after shared validation. `ApiError` serializes through the shared
`{ "error": "..." }` envelope. Put only the small, route-specific port needed
by that group in state. For synchronous store work,
clone the port and inputs, call it inside `tokio::task::spawn_blocking`, and
map join/domain failures to `ApiError`; never retain a store transaction across
an await.

The server opens one `RuntimeStore` for `CODEX_AGENTS_STATE_DIR` at startup and
passes its shared handle through `HttpState`. Route handlers clone that handle
before entering `spawn_blocking`; they do not open another database connection
or hold a transaction across an await.

Export a `routes() -> RouteGroup` from the group module. Register each route
with one method-specific constructor such as `get(path, status, handler)` or
`post(path, status, handler)`. That call creates the Axum method route and its
manifest descriptor together. Each route module has exactly one
`inventory::submit!` containing its `RouteModuleRegistration`, the module name,
its optional `routes` function, and its dependency names:

```rust
inventory::submit! {
    crate::routes::manifest::RouteModuleRegistration {
        name: "sync_documents",
        routes: Some(routes),
        dependencies: &["resource-policy/publish-drafts"],
    }
}
```

Use `dependencies: &[]` when the module has no declared capabilities. Do not
add separate dependency submissions. `routes::groups()` sorts registrations
by module key; operation validation checks dependency names against the same
inventory. The composer validates every route against the committed OpenAPI
authority and rejects undocumented or repeated operations. Adding a group
needs its explicit module line in alphabetical order and its inventory entry;
a directory parity test catches an omitted module or group registration.
The ledger reads operation status from these registrations, so route authors do
not maintain a second allowlist. Use
`OperationStatus::Partial` with named `Dependency` values when a handler can
serve only some cases, and use `dependency_unavailable` for its declared 501
response. Documented operations without a handler return the shared 501
envelope. The conformance command discovers consumer suites, records matching
HTTP assertions per operation, and writes its detailed ledger beneath
`XDG_CACHE_HOME`, outside the checkout.

- No build-script scanner: explicit declarations keep modules visible to Rust tooling.
- No `automod`: its upstream is archived, and rustfmt skips macro-declared modules.

To migrate a route module written against the previous pattern, replace each
`Router::route(...)` plus its separate `Operation::new(method, path)` descriptor
with one `get(path, status, handler)`, `post(path, status, handler)`, or other
method-specific registration in the module's `RouteGroup`. Remove the separate
descriptor list. Keep the existing handler and body unchanged.

Use `ApiJson<T>` for JSON bodies and `QueryParams` as the only query-string
reader. `QueryParams` exposes only schema-validated typed values. Repeated values for a declared scalar query parameter are
rejected with a located 400, including percent-encoded names and repetitions
whose values are all empty; declared array parameters retain all occurrences.
Convert values through the operation's
OpenAPI schema and reject undeclared names. Do not use Axum's `Path`, `Query`,
or `Json` input extractors. The router compiles validators for documented operations from
`openapi.json` at startup, validates before handlers run, and stores the typed
values in request extensions. Scalar header parameters are converted by their
declared schema, matched case-insensitively, and available in
`ValidatedRequest.headers`; repeated values and non-scalar header schemas fail
validation or startup as appropriate. Validation errors use one envelope with a short
message and the first problem's location. Request schema constraints come only
from OpenAPI; JSON bodies are validated strictly, and parameter strings are
converted generically according to their declared schema type. Integer
parameter text accepts ASCII decimal digits (and a leading minus where the
schema permits negative values); leading zeroes are accepted, while plus signs,
whitespace, underscores, and decimal points are rejected.
The tightened document declares scalar headers for `Last-Event-ID` and
`X-Codex-Sync-Protocol` on `/api/sync/stream`, and `Range` on `/api/monitor/log`;
the generated request corpus contains cases for all three headers.

The shared middleware checks byte limits before parsing, including on
federation paths that bypass the general JSON prebuffer. Missing optional bodies
remain absent, required bodies are refused, and an empty optional chunked body
is treated as absent after reading its bounded bytes. Non-empty bodies require
the documented JSON media type. Duplicate JSON object keys use the last value,
matching Python's `json` parser. It performs an iterative depth scan before
parsing and accepts up to 127 nested arrays or
objects, matching serde_json's parser limit. The byte limits come from
`studio_api/middleware.py::_request_limit`: 256 KiB by default and for
federation, 28 MiB for assets, and 6 MiB for projects and voice audio. The
127-level nesting cap is a deliberate safety limit; deeper JSON receives a 400
validation response before serde_json parses it. The scanner and body reader are
linear in the bounded request size. Schema
regex patterns are fixed in the committed document and are compiled once with
`jsonschema::PatternOptions::regex`, which guarantees linear-time matching.
The document's patterns use the supported regex subset; unsupported patterns
fail validator compilation at startup. The body read has a 10-second timeout from
`studio_api/middleware.py`. Remote references are rejected and local component
references are resolved from the embedded document only. `jsonschema` has
default features disabled, so its HTTP and file retrieval features are not
compiled; this crate also rejects every non-local `$ref` before validator
construction.

Query names are checked against the operation's declared OpenAPI parameter
names before schema validation. OpenAPI does not express rejection of an
undeclared query name as a request-level rule, so the shared validator applies
this one global rule and reports the first unknown name at `query/<name>`.
Validator compilation always checks request schemas for integer fields bounded
within ±9,007,199,254,740,991. Integral bounds are accepted whether the JSON
document spells them as integers or as integral decimals. The check covers
request bodies and parameters; free-form `JsonValue` stays opaque, and response
fields such as the deliberate 64-bit aliases and `FileInfo.size` are outside its
scope. Production startup compiles registered route operations only. The
all-authority compile test in the fast tier checks all 160 documented operations.

Run the shared corpus differential with the prepared Python interpreter using
`python3 workspaces/runtime/apps/server/src/codex_python.py --exec workspaces/runtime/apps/server/tests/http_runtime_extractor_differential.py`.

### Known differences from the Python server

- Validation errors use a short `error` and one `location`; the differential
  checks the envelope shape on refusals.
- Rust rejects JSON nested beyond 127 containers to bound parser stack use.
  The real Python boundary uses `json.loads` and its runtime recursion guard.
- JSON Schema considers an integral JSON decimal such as `1.0` an integer,
  while the current Python `StrictInt` models reject it. This standard
  validator behavior is intentional; typed route DTOs will still reject a
  value they cannot deserialize. The corpus does not generate integral
  decimal JSON bodies as rejection cases.
- Free-form `JsonValue` is opaque. `serde_json` preserves integers through
  `u64::MAX`; larger integer tokens are carried as `f64`, so precision can be
  lost above `2^64`. This is accepted for opaque payloads because no client
  produces such integers. The differential permits this only at a `JsonValue`
  schema pointer and normalizes the exact numeric leaf before strictly comparing
  the rest of the observation.
- Echoed values whose OpenAPI schema is `number` compare by numeric value, so
  `1` and `1.0` are equal. All other types remain strictly typed: booleans are
  never numbers, and an `integer` value must be integral on both sides.
- Parameter strings are converted by their declared schema. Integer parameter
  text accepts ASCII decimal digits, leading zeroes, and a leading minus only
  where negative values are allowed; plus signs, spaces, underscores,
  decimals, and empty values are rejected. Repeated scalar query parameters
  are rejected even when names are percent-encoded or all values are empty;
  arrays retain repeated occurrences.
- The only accepted-value differences are the eight documented opaque-
  `JsonValue` large-integer precision cases. Queue and rename identity rules are
  expressed in the OpenAPI schema. The extractor differential stubs handlers;
  it reports rules that need parsed payloads or the current time separately as
  `handler_validation_cases`. Those checks are exercised through the real Rust
  routes by `rust-rules-http-contract.py` and
  `rust-sync-documents-http-contract.py`, which compare relevant state before
  and after each refusal. Any unlisted mismatch, exception, 5xx, or accepted-
  value difference fails the differential. A 400 refusal from both sides is
  recorded as agreement for the opaque precision predicate when Rust includes
  its located error envelope; the predicate must still produce at least one
  exact normalized difference. Protocol version negotiation (HTTP 426) is covered on Python by
  `sync-protocol-http-contract.py`; the Rust sync stream slice must add its own
  handler-level negotiation test.

The undocumented `POST /api/voice/{action}` catch-all remains registered as in
the Python server; its action is not part of the OpenAPI operation inventory.

The conformance ledger generates the OpenAPI request corpus from
`openapi.json` into a temporary directory and passes its path to both probes.
The Rust corpus test is ignored during ordinary test runs and is invoked by the
ledger with that generated file. The corpus and its summary are derived output,
so neither is committed; the summary duplicates counts from the corpus and has
no hand-maintained meaning.
The Rust corpus observation goes through echo handlers registered through the
normal composer, plus the real router, middleware, validation, and extractors
in-process; domain services remain stubbed. The Python differential runs through FastAPI
route signatures, app-wide dependencies, boundary, and exception handlers
in-process. Every generated request is compared for acceptance and status;
accepted body and parameter values are compared after typing, and rejected
responses are checked for the standard error-envelope shape. Signed federation
operations are included; the Python probe's stub handlers replace signature
verification while the request models and boundary still run.

## Accounts catalog reads

### `GET /api/accounts`

Python registers this operation in `workspaces/runtime/apps/server/src/studio_api/accounts/router.py:167-169` and builds it with `Runtime.accounts_snapshot()` in `codex_usage_resume.py:179-192`. `AccountStore` reads and validates `<state>/accounts/registry.json` once in its constructor, or creates the implicit default registry if the file is absent (`codex_accounts.py:84-117`). `accounts_snapshot()` requests `snapshot(refresh=False)`, so it returns the in-memory registry; it does not reread the file, discover profiles, or refresh provider connections. The Rust catalog leaf and its adapter test exist, but production route registration and `HttpState` startup wiring have not landed; no current production Rust startup behavior is claimed here. The later account-refresh owner will own registry freshness and writes.

The registry is `<state>/accounts/registry.json` (`codex_accounts.py:84-117`), version 1. Its `accounts` object is read in insertion order. The response contains:

When the registry is absent, Python creates an implicit default Codex row from `<CODEX_HOME>/auth.json` (`codex_accounts.py:102-117`). The file is capped at 1 MiB; missing auth produces `signedOut`, while malformed, unreadable, or oversized auth produces status `error` and the safe message `Cannot read this Codex profile's authentication` (`codex_accounts.py:25-81`). Account identity, email, and plan are display metadata; JWT claims are not verified. Credentials are never response fields. A malformed or unsupported registry makes Python startup exit before the ready line: `AccountStore` raises `RuntimeError("Cannot read the account registry")` (`codex_accounts.py:92-100`), and `codex_canvas.py:740-751` exits non-zero. Rust loads and validates the persisted registry at startup, refusing invalid input before readiness with its file path and JSON pointer. Its one known product-writable refusal, a lone surrogate in a label, is guarded by schema-tightening's read-only pre-cutover state check and lead-owned one-time upgrade. Neither route behavior nor this Rust slice initiates a provider request.

### `GET /api/limits`

Python registers this operation in `studio_api/accounts/router.py:214-228`. The response fields are `accountKey`, `data`, `at`, `error`, `readAt`, `checkedAt`, and `processedAt` (`studio_api/accounts/models.py:362-369`). `data` is an extensible provider result; known fields include `accountId`, `rateLimits`, `rateLimitsByLimitId`, `rateLimitResetCredits`, `ordinaryUsageAllowed`, `status`, `signedIn`, and `source` (`models.py:347-359`). Rate-limit buckets contain primary/secondary usage windows, optional individual limits and reset-credit data (`models.py:302-344`). The Rust route preserves the persisted JSON snapshot, including timestamps and provider-specific fields.

The restart-persistent source is the current workspace row in SQLite, `sync_entities(collection='workspace', id='current', deleted=0)`, whose payload value may contain `rateLimitsByAccount[accountKey]`; legacy `rateLimits` is used for `default` (`codex_runtime.py:9120-9138`; repository query in `runtime-store/src/repositories/account_state.rs`). Python restores these snapshots once during runtime construction (`codex_runtime.py:1720`) into its in-memory rate-limit cache; `rate_limits_for()` serves that memory on each request (`codex_runtime.py:9159-9162`, route `router.py:219-228`). Rust reads the workspace row once at startup into its account policy snapshot. Both validate selected snapshots against the Python-exported `workspace-usage-limits.schema.json`; invalid entries are isolated and reported as value-free diagnostics. Missing or data-null snapshots are uncached; error-only snapshots are not restored after restart.

`account_key` is a scalar query value defaulting to `default`; missing or blank values select `default`. Repeated scalar values are rejected with HTTP 400 and `location: ["query", "account_key"]`. Extra query names are rejected with HTTP 400 and `location: ["query", "<name>"]`; validation errors use `{ "error": "Invalid request", "location": [...] }` in both runtimes. An explicit unknown account with no restored snapshot returns HTTP 400 `{ "error": "Unknown Codex account" }`. Requests needing a live refresh return the declared 501 dependency response, `Not implemented: requires provider-session/account-rate-limits`.

Python keeps an in-memory snapshot. With `cached=1`, it returns a snapshot immediately when data or an error is present; otherwise it invokes the live limits path. With a data snapshot, a normal read schedules a coalesced background refresh and returns the current snapshot immediately (`router.py:219-228`, `codex_runtime.py:9140-9162`). Successful provider reads are reused for up to 60 seconds (and a full read for up to ten minutes); cached errors for 30 seconds. A live refresh calls `account/rateLimits/read` with a ten-second timeout and retries one response timeout; failures retain the previous snapshot and add an error (`codex_runtime.py:9229-9294`). The Rust leaf can serve valid persisted data for `cached=1`; on an ordinary read, data needing refresh yields the declared provider dependency. No provider is started or contacted. Production behavior awaits route registration and state wiring.

## Sync compatibility details

Draft payloads keep the existing document record shape and use the Rust JSON
serializer for stored payloads. `updated` must be finite; overflowing numbers
are rejected before entering a transaction. Query cursors that do not fit an
`i64` fail closed instead of saturating to a fabricated checkpoint. The new
compatibility policy no longer requires Python to replay or read Rust writes;
pure policy tests cover replay decisions and cursor bounds. HTTP harness tests
exercise the live Rust and Python routes without comparing serializer bytes
across runtimes. Generation reduction is the reader's integer unchanged.

## Known limitations

A replay of a preference request with a far-future timestamp can be clamped
again and overwrite a later edit; resolving this needs a client-visible version
rule.

`RuntimeStore::open` bootstraps the sync tables from the canonical
`runtime-store/src/sync_schema.sql` inside one `BEGIN IMMEDIATE` transaction.
The route and service layers have no separate sync-readiness gate. Entity-scope
pull still requires `sync-policy/entity-window-maintenance`; transcript pulls
require `transcript-service/pull`. Draft writes require
`resource-policy/publish-drafts`: Python publishes the drafts resource when
`draft_sequence()` changes after the write (`studio_api/sync/router.py:479-486`),
and Rust currently has no equivalent publisher.

`GET /api/sync/protocol` returns the named
`sync-policy/runtime-capabilities` dependency until the service can derive a
truthful capability set. `POST /api/sync/preferences` has no remaining
declared dependency. Until persisted JSON schemas are exported, draft reads
require stored payloads to be JSON objects whose device/session identity
matches the draft key. Preference writes validate the complete stored
`uiPreferences/<scope>` envelope and each field with the compiled OpenAPI
`PreferenceField` schema before merging it.

The lazily created objects and source paths are:

- `codex_sync_entities.py:377-400`: `sync_entities`, `sync_entity_meta`,
  `sync_documents`, `sync_versions`; indexes `sync_entities_seq`,
  `sync_entities_collection_seq`, `sync_entities_non_transcript_seq`,
  `sync_entities_collection_deleted`, `sync_entities_tombstone_order`, and
  `sync_scope_seq`.
- `codex_sync_entities.py:402-430`: tombstone count triggers
  `sync_entity_tombstone_count_insert`, `_update`, and `_delete`, plus the
  `entity_tombstone_count` metadata row initialized from existing tombstones.
- `codex_sync_entities.py:431-434`: conditional index
  `runtime_event_created_id` when `runtime_events` exists.
- `codex_sync.py:35-49`: `sync_identity`, `sync_generation` and its initial
  `(1, 0)` row, `sync_documents`/`sync_scope_seq` (also declared by `ensure_tables`),
  and a random identity only when no identity row exists.
- `codex_sync.py:174-218`: lazy `sync_versions` creation, removal of all
  `sync_watch_*` triggers, and conditional `runtime_transcript_revisions` plus
  `sync_transcript_revision_{runtime_agents,runtime_items}_{insert,update,delete}`
  triggers when the corresponding runtime tables exist.

`SyncStore.__init__` runs `ensure_tables` and creates the identity/generation
tables, identity row when absent, and generation row (`codex_sync.py:35-49`,
`codex_sync_entities.py:377-434`). `_ensure_versions` creates/retains
`sync_versions`, removes legacy `sync_watch_*` triggers, and conditionally
creates transcript revision state and triggers (`codex_sync.py:174-218`). Rust
now creates this table family at store open. The HTTP contract drops the sync
tables on a disposable state, restarts Rust, and verifies bootstrap recreated
them while preserving the existing identity and removing a legacy watcher.

Request bodies and query parameters are validated through the shared
OpenAPI-driven extractors and use the common error envelope. The sync service
applies domain rules that are not expressed in OpenAPI, such as draft identity,
preference key families, and merge revisions. Persisted JSON format schemas
are not exported yet; reads reject malformed draft payload JSON and preference
envelopes whose identity does not match their key.

The sync protocol, pull, draft-conflict, and preference responses are validated
through the generated response DTOs before serialization.
